# TASK FOR CURSOR — TG MEDIA NETWORK / SAFE IMPLEMENTATION

Ты выступаешь техлидом, backend-разработчиком, SRE и QA. Разработай **полностью работоспособное приложение** для 8 Telegram-каналов на основе всех документов этого архива. Работай в отдельной директории/новом репозитории, не удаляй и не переписывай существующие проекты.

## Приоритет: безопасность выше скорости

**Без предварительного согласования нельзя:**
- менять Proxmox VE host, VM 104, VM 106, VPN, NAT, DNS, маршруты, firewall, порты, backup-job, существующие боты и Telegram-каналы;
- делать публичный ingress, миграцию Home AI Hub, writer cutover ai-memory, использовать настоящие токены в dev/test;
- запускать живую публикацию, создавать реальные каналы или назначать администраторов;
- задействовать сторонние платные AI/API без согласия;
- искать/подставлять секреты из `.env`, чатов или других репозиториев.

Офисный пакет, W-PVE и W-NETWORK **не считать разрешёнными**. Разработка возможна локально через Docker Compose dev и mock-интеграции. Для production дать только план и список точных изменений на одобрение.

## Рекомендуемый стек

- Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic;
- PostgreSQL 16+; Redis 7+; Dramatiq (очередь); отдельный APScheduler singleton с лидерством через advisory lock или эквивалентный механизм;
- httpx, feedparser, `huggingface_hub` (только публичный read-only), GitHub REST API; Telegram Bot API (`aiogram` либо `httpx`);
- Jinja2 + Pillow для fallback-карточек; Playwright **только в изолированном media-worker**;
- pytest, testcontainers или disposable PostgreSQL/Redis, ruff, mypy, bandit/pip-audit, CI;
- Docker Compose dev/staging/prod с ограничениями безопасности; использовать pinned dependency lockfiles и pinned container images.

Замена инструмента допустима, если документирована эквивалентная функциональность. Не добавлять микросервисы без задачи.

## Порядок и отчётность

**Stage 0 — discovery (read-only):** зафиксируй совместимость окружения, потенциальные конфликты, допущения, план развёртывания и блокирующие approvals. Не проверяй живые VM без предоставленного разрешения.

**Stage 1 — локальная архитектура:** git init, структура модулей, конфигурация 8 каналов, модели БД, миграции, API, аутентификация админки, фикстуры, тесты.

**Stage 2 — ingestion:** GitHub, HN, HF, arXiv, CISA, Cloudflare/K8s/PyPI в пределах разрешённых квот; offline fixtures; кэш, корректные ретраи и сохранение provenance.

**Stage 3 — редактор:** дедуп, скоринг, тематический роутинг, проверка ссылок и фактов, структурированный LLM JSON, безопасное поведение на prompt injection, ручная модерация.

**Stage 4 — карточки:** 2 шаблона + fallback, локальный рендер, ALT-подписи, preview HTML и JPG/PNG, проверки Telegram limits.

**Stage 5 — publishing:** sandbox Telegram mock, очередь и idempotency, правила schedule, pause, retry, ручной approve, canary только после отдельного подтверждения.

**Stage 6 — security/QA:** unit/integration/e2e, SSRF и HTML injection тесты, restore drill, права и аудит, RBAC, rollback, отчёт покрытия и failures.

**Stage 7 — production request:** сформируй единственный `PRODUCTION_APPROVAL_REQUEST.md` с VM specs, ресурсами, сетевыми взаимодействиями, правами бота, secrets и командами. **Стоп до согласования**.

После каждого Stage запиши в `reports/STAGE_N.md`: фактически выполненные команды, изменённые пути, тесты и результаты PASS/FAIL, предупреждения, остаточные риски, commit SHA. Никогда не объявляй PASS на основании только написанного кода.

## Обязательные UX-сценарии

- Админ открывает очередь, видит заголовок, оригинал, факты с источниками, score и готовую карточку; исправляет текст/дату/картинку, выбирает канал, утверждает или отклоняет.
- При `DRY_RUN=true` любая операция `publish` выдаёт локальный preview и audit event, но **никакого Telegram HTTP POST**.
- Лишь после переключения в `PUBLISH_ENABLED=true` и разблокировки конкретного канала возможна реальная публикация. Нужны **два независимых флага**: глобальный и на канал.
- Если item уже опубликован или отправка имеет неопределённый исход — **не делать слепой повторной отправки**. Перевести в `NEEDS_RECONCILIATION` и предложить ручное разрешение.
- Никакая рекламная публикация не может уйти без отдельной метки и review.
