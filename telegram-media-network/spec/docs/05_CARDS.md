# 05. Карточки и Telegram UX

## 5.1 Макет публикации

Telegram-формат по умолчанию: **одно изображение + нативная подпись** (`sendPhoto`) и опциональная inline-кнопка «Источник» (URL). Это не HTML-страница и не «богатая карточка» с произвольным оформлением текста. Кнопка/URL строятся только из проверенного allowlist URL.

**Формат A `tool`:** верхний бренд-бар канала, логотип/метка GitHub либо крупный скриншот приложения, короткий заголовок, категория, 1–2 факта/тега, чистый нижний отступ. Применение: GitHub, AI Tools, DevPulse, HomeLab.

**Формат B `news`:** заголовок, дата, один яркий визуальный объект/иллюстрация, бренд-бар. Применение: AI news, TechnoFuture, Infra.

**Формат C `security`:** крупные `CVE-...`, подпись `ОБНОВЛЕНИЕ/УЯЗВИМОСТЬ`, важность только по подтверждённым данным (не придумывать CVSS), чёткие действия «проверить версию/обновиться»; тревожный стиль без сенсаций.

Обязательны: единая узнаваемая типографика, хорошая читаемость на телефоне, контраст, ограничение текста на картинке до 15–20 слов, `ALT`/доступное текстовое описание в материале для UI. Не делать мелкий технический текст частью изображения; деталь — в подписи.

## 5.2 Технический контракт

- Экспорт `JPEG`, `PNG` (предпочтительно итоговый JPEG 1280×720, цветовое пространство sRGB). Источники 16:9, кроп с safe zone, без нарушения соотношения.
- Проверять ограничения актуального Telegram Bot API `sendPhoto`: фото до 10 MB, сумма width+height ≤10000, aspect ratio ≤20, подпись от 0 до 1024 символов после entities parsing. **Свой** внутренний лимит `≤900` видимых символов до URL/меток.
- Для caption использовать HTML-парсер с escape всех вставок, только allowlisted tags; безопаснее сформировать `caption_entities` для ссылок, но валидировать byte/char limits. Не принимать от LLM готовый неэкранированный HTML.
- Media hashes SHA256, content type magic проверка, удалять EXIF, ограничивать пиксели/размеры на входе, блокировать SVG/scripts как загружаемый remote media.
- Preview показывает реальный финальный caption и публикуемый файл, а не отличающийся мокап. Сервер хранит `render_version` и `caption_hash`.

## 5.3 Приоритет изображений и права

1. Изображение, на которое у оператора имеется явное право использования (например, собственный шаблон или лицензия с допустимым reuse/attribution).
2. Превью приложения или скриншот страницы только при разрешённой политике и после проверки прав/ToS; не копировать «просто любую картинку из OG». Внешняя OG-картинка — **источник потенциального изображения, не лицензия**.
3. Собственная векторная/типографическая иллюстрация по шаблону (обязательный fallback без внешних ресурсов).

При сомнениях — fallback. Для GitHub не делать скриншот секретных/private репозиториев; `playwright` разрешать только на прошедших allowlist URL в контейнере без доступа к локальной сети и credential material.

## 5.4 Подпись

Пример (синтетический):

```text
🛠 Проект ExampleTool выпустил версию 2.4

Утилита помогает отслеживать изменения Docker Compose-конфигураций. В релизе заявлены сравнение файлов и отчёт об изменениях — это подтверждено официальным changelog.

Кому полезно: администраторам небольших self-hosted серверов.

Источник: github.com/example/exampletool/releases/tag/v2.4
#opensource #homelab
```

Системная проверка: текст должен быть уникальным, с кликабельным source URL, не менее одного подтверждаемого факта. Если `license_unknown` — нельзя ставить #opensource как утверждение о лицензии. Хэштеги 1–3, только релевантные.

## 5.5 Видео/анимация и изображения с AI

MVP — только фото. Видео, карусель, анимированные обложки — out of scope. Не тратить GPU/облачные API на случайные иллюстрации; HTML+Pillow обеспечивают воспроизводимый бренд, локальные ресурсы и низкую себестоимость.

## 5.6 Что входит в design assets

`design/card_template.html` — пример синтетической карточки `tool`. Cursor обязан создать минимум 8 бренд-вариантов (по одному каналу) и 3 композиции (news/tool/security), тесты переноса длинных названий и текстов с кириллицей; PNG/JPG previews в `reports/screenshots/` при разработке. В архиве **не содержатся готовые фирменные логотипы** — итоговые стили создаются при реализации.
