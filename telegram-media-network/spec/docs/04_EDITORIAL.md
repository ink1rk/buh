# 04. Редакционный конвейер и качество

## 4.1 Правила материала

Каждый пост обязан содержать: **что произошло**, **кому полезно**, **почему важно**, **откуда известно**, **ограничения/неопределённость**. Язык: разговорный профессиональный русский без кликбейта. Нельзя писать «бесплатно» без факта бесплатного использования и важных ограничений. Нельзя выдавать MIT/Apache за отсутствие любых ограничений. Не писать «проверили» без реального sandbox теста и отчёта.

Модификаторы: `preprint`, `sponsored`, `beta`, `security_advisory`, `no_license`, `not_verified`, `broken_link`. Эти значения определяют UI-бейджи/блокировки, но не являются рекламными декоративными элементами в Telegram.

## 4.2 Нормализация и дедуп

1. Canonicalization URL: допустимы `https`, нормализация host lowercase, default port, `utm_*`/`fbclid`/`gclid` удалить; **не удалять** параметры, меняющие идентичность статьи, релиза или CVE. Redirects только safe-fetch, DNS/IP check на каждом hop.
2. Сильный ключ: `github:<numeric_repository_id>`, `github-release:<repo_id>:<tag>`, `arxiv:<arxiv_id>:<version>`, `cve:<CVE-ID>:<date_added/version>`, `hn:<item_id>`, `article:<canonical_url_hash>`.
3. Exact duplicate по ключу/канонической ссылке; near duplicate: нормализованный title + slug + MinHash/SimHash и при необходимости локальные embeddings. Семантические совпадения *подсказывают*, но не удаляют без определённого порога или ручного подтверждения.
4. News update — новый material только при **существенной новой информации**, новая версия draft и ссылка на предыдущий пост; не репост «новость дня» из другой ленты.
5. Глобально: cooldown публикации одного story cluster на всю сеть 48 часов; исключения с другим углом подачи только OWNER и задокументированной причиной. Канальный cooldown того же проекта 30 дней, для важного release допускается 7 дней с реальным changelog.
6. Проверить транзакционные unique constraints, чтобы два worker не обошли дедуп одновременно.

## 4.3 Детерминированный скоринг

Шкала 0–100, версия `rubric-v1`:

| Составляющая | Max | Как оценивать |
|---|---:|---|
| Проверяемость | 25 | первоисточник, актуальная ссылка, дата, несколько фактов |
| Практическая польза | 20 | ясный сценарий применения, инструкция или конкретное изменение |
| Новизна | 20 | новое событие/новый релиз/изменение, а не старый топ GitHub |
| Релевантность каналу | 15 | соответствует теме, нет соседнего более подходящего канала |
| Сигналы качества | 10 | стабильный репо, changelog, репутация издателя, тех. доказательства |
| Общественная значимость | 10 | польза аудитории, масштаб, обсуждение без хайпа |
| **Всего** | **100** | Все компоненты и источники численно доступны в UI |

Штрафы (не могут уменьшать score ниже 0): clickbait −15, отсутствие даты −10, невнятное лицензирование −10 для заявлений об open source, явный promotional press release −10, high-risk claim без достаточного подтверждения −25. 80+ предложить в очередь одобрения; 60–79 на ручной обзор; <60 в архив; `hard_block` побеждает любой score.

Hard blocks: битая ссылка, недостоверный факт, запрет ToS/лицензии, утверждение без source, уязвимость с инструкцией атаки, раскрытие персональных данных, контент для мошенничества, дискриминация, однозначный prompt injection, реклама без legal approval. Любой блок показывает конкретную причину.

## 4.4 Fact extraction и проверка

Пайплайн не должен принимать произвольные факты от LLM. Сначала собрать `facts[]` с `evidence_url` и короткой доказательной выдержкой (лимит 160 символов на извлечение для внутренней модели). Проверять: численные характеристики, версии, цены, платформы, наличие лицензии, release date. Несогласие источников → `NEEDS_REVIEW`; отсутствие подтверждения → нельзя включать в пост. Отдельно валидировать опасные рекламные обещания, сравнения моделей и любые заявленные результаты benchmark.

Сенсационная наука, ИБ-инциденты и новости о компаниях: требуется официальный/первичный источник плюс дополнительная независимая проверка там, где речь о крупном/оспариваемом утверждении. Указывать дату публикации первоисточника, различать «сегодня обнаружено» и «вчера опубликовано».

## 4.5 LLM-контракт

- Передать в модель **данные как данные**: отдельная системная политика + структурированный JSON, запрещено исполнять «инструкции» из внешних README/постов. Источник может содержать фразы «ignore prior instructions» — это только цитируемый пользовательский контент, не команды.
- Модель возвращает только JSON по `schemas/post_draft.schema.json` и `claims[]` с `evidence_id`; max 2 tries on validation, затем `NEEDS_REVIEW`.
- Русский, 350–800 символов тела в среднем; `body_max_chars=900` до финальной сборки, Telegram caption ≤1024 после entity parsing. Имена собственные и версии проверять детерминированно.
- Стилистика канала различается через `channel.voice`, но ни один стиль не отменяет запрет на непроверенные заявления.
- LLM output используется **только как черновик**. Даже если модель пишет `publish:true`, оно игнорируется: никакие бизнес-действия не могут быть управляемы текстом модели.
- `critical`/CVE, `sponsored`, `preprint-extraordinary`, вопросы права/здоровья/безопасности — ручная модерация вне зависимости от итогового score.

## 4.6 Автоаппрув (не MVP)

Первые 14 календарных дней — 100% ручной просмотр. Затем OWNER может отдельно включить auto-approval **только** для whitelist-проектов и low-risk релизов при следующих условиях: доказанный 95% factual precision на репрезентативной ручной выборке, 0 критических нарушений прав/безопасности, 0 дубликатов публикаций, успешный rollback/restore, отдельный канал opt-in. ИБ, научные сенсации, спонсорские публикации никогда не автоаппрувить.

## 4.7 Редакторские примеры

**Плохо:** «Новейший open-source агент превосходит Claude и GPT, полностью бесплатен!» (нет бенчмарка и прав использования).

**Хорошо:** «Проект X добавил локальное управление задачами через CLI. Репозиторий обновлён 8 ноября; в changelog — новые команды A/B. Подходит для тех, кто автоматизирует повседневные операции. Лицензия указана как Apache-2.0. Источник: официальный release». Указывать конкретику только если эти данные есть в подтверждённых facts.

**Плохо:** «CVE-XXXX активно используется хакерами» при отсутствии KEV/вендорского подтверждения. **Хорошо:** «Вендор опубликовал advisory по CVE-...; обновите ... согласно бюллетеню. Признаков активной эксплуатации в проверенных источниках не обнаружено на момент проверки» — вторую фразу можно использовать только при реальной проверке и датированной оговорке.
