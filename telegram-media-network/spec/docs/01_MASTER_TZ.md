# 01. MASTER TECHNICAL SPECIFICATION

Версия 1.0 · 10.11.2026 · Кодовое имя `telegram-media-network` · Владелец продукта: заказчик · Разработчик: Cursor.

## 1. Цель и продуктовые границы

Создать централизованную автоматизированную редакцию для сети из восьми русскоязычных Telegram-каналов. Конвейер: **легальный сбор публичных метаданных/коротких фрагментов → нормализация → проверка источника → удаление дублей → определение темы → редакционный скоринг → генерация авторского RU-текста → иллюстрация → одобрение → планировщик → публикация → контроль → аналитика**.

Идея не в бессистемном копировании: каждое сообщение даёт читателю новую проверяемую информацию и объясняет практическую пользу. Разработка автономна от Home AI Hub, хотя впоследствии может вызывать отдельно согласованный локальный inference endpoint.

### Out of scope MVP

Автоматическая покупка рекламы, сбор личных данных подписчиков, неофициальные userbot/MTProto-сессии, рассылки в личные сообщения, накрутка аудитории, парсинг закрытых аккаунтов, обход paywall/robots/captcha, дообучение LLM, публичная веб-панель, автоматическое создание Telegram-каналов, скачивание/запуск непроверенного кода из найденных репозиториев, модификации Proxmox/сети без согласия.

Начальный план — до 16 публикаций/сутки для всей сети; отсутствие качественных кандидатов = допустимый пропуск, никакой выдуманной новости ради плана. После двухнедельного испытания разрешить индивидуальный рост до 3–5/сутки при сохранении качества. Все названия рабочие: usernames, права и наличие каналов проверяются при вводе в эксплуатацию.

### Правило разведения тем

- Новый LLM-релиз → `ai_news`; репозиторий с удобной оболочкой над LLM → `ai_tools` или `github`, но **по умолчанию только один канал**.
- Уязвимость в Kubernetes → `cyber` как факт угрозы, `infra` только как отдельно написанная инструкция по безопасному обновлению; автодублирование запрещено.
- Self-hosted медиасервер → `homelab`; если это прежде всего инструмент разработки → `dev`.
- Важные исследования без peer-review — указывать `preprint / не рецензировано`, не выдавать за доказанный результат.

## 3. Участники и разрешения

`OWNER` — владелец настроек, интеграций, публичного режима; `EDITOR` — правка/одобрение обычных постов; `REVIEWER_SECURITY` — подтверждение ИБ-постов; `VIEWER` — чтение очереди и метрик; `SERVICE` — операции конвейера. Ни одна учётная запись не может расширять собственные права, а изменения роли фиксируются в audit trail.

В MVP аутентификация локальной админки через OIDC при наличии готового, согласованного провайдера; иначе отдельная локальная учётная запись с Argon2id, TOTP MFA и безопасными сессиями; localhost-only по умолчанию. Не использовать общие admin-аккаунты.

## 4. Функциональные требования (проверяемые)

- **FR-001 Sources:** Конфигурация ≥8 каналов, ≥7 независимых read-only адаптеров источников, доступность ручного ввода/blacklist. У каждого источника есть политика, бюджет, статус и `last_success_at`.
- **FR-002 Ingest:** HTTP conditional GET (`ETag`,`Last-Modified`) где применимо, таймауты, backoff, JSON/RSS валидация, хранение короткого исходного payload/provenance и даты; отсутствие потенциально опасного активного контента.
- **FR-003 Routing:** Multi-label классификация, основной канал + альтернативы, объяснимая причина; вручную можно переместить публикацию.
- **FR-004 Dedup:** exact/near-dup и глобальное окно повторов; atomic unique constraints до публикации; фиксируются связи с оригиналом.
- **FR-005 Ranking:** Score 0–100, прозрачные компоненты, минимальная уверенность и freshness; 80+ кандидаты, 60–79 на обзор, <60 обычно архив; ничто не публикуется при неверифицированном факте.
- **FR-006 Editorial:** Авторский краткий RU-текст, проверка по доказательствам, схема JSON, никакого придумывания фактов/версий/тестов/лицензий; ссылки на 1–3 первоисточника; обязательная квалификация исследовательских гипотез.
- **FR-007 Media:** Рендер 1280×720 или 1200×675, шаблоны news/tool/security, изображения только из разрешённых источников; fallback чисто типографический; технический контроль 10 MB/photo, ratio и 1024 символов подписи по актуальному Telegram API.
- **FR-008 Moderation:** Полный workflow, редакторская web UI, история версий, комментарии, разрешения на approve/reject, рискованные категории require human.
- **FR-009 Scheduler:** Изолированные расписания 8 каналов `Europe/Moscow`, quiet hours, лимиты на день/час, последовательная атомарная отправка, ручное пауза/возобновить, no backlog storm.
- **FR-010 Publishing:** Только Bot API и только отдельно авторизованный бот с `can_post_messages`; режим mock/dry-run; idempotency, 429 retry-after, outcome reconciliation, публикация одной фото + подписи и tracking message_id.
- **FR-011 Observability:** Structured logs, metrics, журнал событий, healthchecks, уведомления владельцу о простоях/ошибках, без секретов и персональных данных в логах.
- **FR-012 Business:** Учёт спонсорских размещений, отдельный approval/legal gate, архив договорных реквизитов вне публичного feed, статистика факт/план/ручной reach; никакой автоматической рекламы до ручного разрешения.
- **FR-013 Admin:** UI для каналов, источников, дублей, истории постов, карточек, публикаций, ошибок, блокировок, рекламы, ручного вставления URL и пересборки; управление secrets только вне UI.
- **FR-014 Export:** JSON/CSV выгрузки метрик и audit trail, выгрузка конфигурации без секретов; restore plan.
- **FR-015 Readiness:** Dev stack полностью запускается без сетевого доступа к Proxmox и без Telegram токенов на test fixtures.

## 5. Нефункциональные требования

- **NFR-001 Availability:** Целевое 99% рабочего времени после pilot; сломанный источник не валит остальные.
- **NFR-002 Throughput:** До 1000 сырых элементов/сутки и 50 публикаций/сутки на одном экземпляре с запасом; performance измерять тестами, это **проектная цель**, не гарантия.
- **NFR-003 Latency:** 95% обычных новостей — в очереди модерации ≤30 минут с момента успешного poll; near-live источники и RSS учитывают задержку самих сервисов.
- **NFR-004 Safety:** Ни один live Telegram request из тестов/DRY_RUN; ни одно скрытое раскрытие токена.
- **NFR-005 Data:** PostgreSQL транзакционность, корректные UTC timestamps, retention, резервные копии, цель RPO ≤24h / RTO ≤4h после настройки и **проверенного restore**; не считать выполненным, пока restore не протестирован.
- **NFR-006 UX:** Мобильная/desktop админка, быстрые фильтры, русский UI, WCAG-inspired контраст, предпросмотр реальной подписи.
- **NFR-007 Privacy:** Только технические метаданные и необходимые права сотрудников; персональные данные читателей не собирать.
- **NFR-008 Cost:** Источники бесплатные, никакой зависимости от платного LLM; optional local inference, CPU fallback в ограниченном режиме.
- **NFR-009 Security:** Изоляция ingress/egress, no privileged containers, non-root, обновления, SBOM, security scans, ручная проверка привилегий.

## 6. Развёртывание с учётом существующего окружения

**Известный контекст (требует read-only верификации после разрешения):** домашний Proxmox VE, Intel i9-13900H, 96 GB RAM и NVMe 4 TB; VM104 Home AI Hub, VM106 GitLab. Проверки резервного восстановления и некоторые изменения прежнего стека не закрыты. Нельзя из этих сведений делать вывод, что VM свободна или что можно менять хост.

Предложение **после отдельного approval**: новая изолированная Ubuntu Server 24.04 LTS VM, ориентир 4 vCPU / 8 GB RAM / 60 GB диска, без GPU, Docker Compose; оперативный резерв 16 GB если нужен локальный LLM на той же VM (лучше отдельный inference-сервис). Это оценка для MVP без нагрузки LLM, уточнить после теста. VMID/сетевое имя/IP не назначать автоматически. API admin UI — `127.0.0.1:8787` на guest, доступ через SSH port forwarding или утверждённый private reverse proxy. Не открывать WAN порты.

LLM варианты: (A) внешний read-only endpoint уже согласованного Home AI Hub **после проверок**; (B) временный local Ollama внутри выделенной VM с ресурсными лимитами; (C) без LLM публикацию только из ручного редактора. Никаких автоматических зависимостей от writer ai-memory или RAG.

## 7. План реализации / критерии перехода

| Gate | Результат | Переход только если |
|---|---|---|
| G0 | Аудит репозитория/допущений | Есть permission matrix и план без изменения текущих VM |
| G1 | Модели данных, dev Compose и API | Миграции/аутентификация/фикстуры PASS |
| G2 | Все source adapters | Offline tests и rate-limit tests PASS |
| G3 | Дедуп+LLM+UI | Accuracy+injection tests PASS; human gate работает |
| G4 | Карточки+Bot API mock | Telegram formatting/image tests PASS; DRY_RUN доказан |
| G5 | Резервирование+операционные тесты | Restore drill и security scan PASS |
| G6 | Staging canary | Отдельное согласование тестового Telegram-канала |
| G7 | Production | Отдельное согласование VM/network/bot/channels/secrets |

На G0–G5 всё возможно выполнить локально. Не переключать production из staging по ходу работы без прямого подтверждения владельца.

## 8. Definition of Done

Принятие только при: код + README эксплуатации + архитектура + миграции + конфиги каналов + тесты + артефакты рендера + retry simulation + dry-run logs + журнал audit + CSV/JSON export + restore report + approval request. Два блока отдельно: `DEV_READY` и `PRODUCTION_APPROVED`. Первый не означает второй.

## 9. Открытые параметры, которые не блокируют код

До ответа: placeholders + mock + DRY_RUN; не угадывать и не брать из других сервисов.
