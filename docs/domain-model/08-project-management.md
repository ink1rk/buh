# 08 — Project Management: CURRENT STATE → TARGET STATE

## 1. Главный принцип

Проект в ITMS — не контейнер для задач. Проект описывает **переход инфраструктуры из текущего состояния в целевое**:

```
CURRENT STATE                 PROJECT                      TARGET STATE
(снимок модели)   ──►  план изменений + работы  ──►  применённая модель
state_snapshot          planned_change + task[]         обновлённая CMDB
```

Из этого следуют три правила:

1. Проект **обязан** ссылаться на объекты инфраструктуры (`project_ci`), иначе он не отличим от заметки.
2. Целевое состояние описывается **структурированно** (`change_item`), а не только текстом.
3. Завершение проекта **обновляет модель**: применение целевого состояния — часть закрытия проекта, а не ручная работа «потом».

## 4. Gantt: что именно реализуется

Требования к диаграмме:

- иерархия: проект → этап → задача → подзадача, сворачивание уровней;
- зависимости всех четырёх типов (FS, SS, FF, SF) с лагом в днях;
- **расчёт критического пути** (CPM): ранние/поздние старты и финиши, резерв времени (float); задачи с нулевым резервом подсвечиваются;
- перетаскивание задачи меняет даты; система показывает каскад: какие зависимые задачи сдвинутся;
- два режима сдвига: «жёсткий» (двигать зависимые автоматически) и «мягкий» (показать конфликт, но не двигать) — выбор пользователя, по умолчанию мягкий;
- baseline: сохранённый плановый график; факт отображается второй полосой — это и есть «план/факт»;
- вехи — ромбы на шкале; просроченная веха красная;
- окраска задач по исполнителю/статусу/приоритету (переключатель);
- масштаб: день / неделя / месяц / квартал.

**Порядок реализации: сначала модель, потом рендерер.** Gantt — самостоятельная сложная задача, и привязывать её к конкретному способу отрисовки на старте нельзя.

1. Сначала делается расписание как доменная модель: задачи, интервалы (`start_date`/`due_date`, план и факт), зависимости четырёх типов с лагом, расчёт ранних/поздних дат, резервов и критического пути. Всё это живёт на сервере в `domain/projects/schedule.py`, покрывается unit-тестами с эталонными примерами и отдаётся эндпоинтом `/projects/{id}/schedule` в виде, не зависящем от отрисовки.
2. Рендерер — сменный слой над этой моделью. Контракт данных (`ScheduleView`: строки, полосы, связи, вехи, шкала) фиксирован, а конкретная реализация (собственный SVG, canvas или сторонняя библиотека) подключается адаптером и может быть заменена без изменения бэкенда и логики.
3. Первая версия интерфейса может быть табличной («расписание списком» с датами, зависимостями и подсветкой критического пути) — она полезна сама по себе и снимает риск того, что визуализация задержит всю фазу.

Практическое следствие: неудачный или медленный рендерер меняется на другой без переделки модели и API; сроки, зависимости и критический путь остаются одним источником истины.

## 5. План/факт и прогресс

| Показатель | Формула |
|---|---|
| Прогресс задачи | По статусу (`DONE` = 100%) либо по доле выполненных подзадач |
| Прогресс этапа | Взвешенно по оценкам задач (`estimate_min`), при отсутствии оценок — по количеству |
| Прогресс проекта | Взвешенно по этапам; вехи не влияют на число, но влияют на статус здоровья |
| Отклонение по срокам | `actual_end_date − due_date` по задачам и вехам |
| Отклонение по трудозатратам | `Σ spent_min − Σ estimate_min` |
| Отклонение по бюджету | `budget_actual − budget_planned` по статьям |
| Здоровье проекта | Правила: просрочки, риски, критический путь, ближайшая веха — см. §9 |

Прогресс никогда не вводится вручную: это производная величина. Ручной ввод процента выполнения — главный способ получить недостоверный отчёт.

## 6. CURRENT STATE: фиксация

`state_snapshot` — нормализованный срез подграфа модели на момент времени.

```json
{
  "scope": { "location_path": "org/site-north/bld-a/fl-2/room-205",
             "include": ["ci","rack_mount","interface","connection","power_node","power_link"] },
  "taken_at": "2026-09-22T08:00:00Z",
  "checksum": "sha256:…",
  "payload": {
    "ci": [ { "id": "…", "code": "SRV-1C-01", "ci_type": "DEVICE", "status": "ACTIVE", … } ],
    "rack_mount": [ … ],
    "power_node": [ … ],
    "power_link": [ … ],
    "totals": { "devices": 24, "estimated_load_w": 16800, "racks": 2 }
  }
}
```

Назначение:
1. Зафиксировать исходные данные проекта, чтобы расчёты «до/после» были воспроизводимы.
2. Дать возможность сравнить, что реально изменилось за время проекта (в том числе — что изменилось помимо плана).
3. Приложить к документам согласования как «состояние на дату».

Снимок иммутабелен. Он не заменяет аудит (аудит — история поштучных правок), а даёт целостный срез.

## 7. TARGET STATE: структурированный план

Целевое состояние — набор `change_item`, каждый из которых является элементарной операцией над моделью:

| Операция | Сущность | Пример payload |
|---|---|---|
| `CREATE` | `ci` (DEVICE) | модель R650, имя SRV-1C-03, владелец, статус PLANNED |
| `CREATE` | `rack_mount` | стойка R2, U14–U15, фасад FULL |
| `CREATE` | `power_node` (PSU ×2) + `power_link` | подключение к PDU R2-A и R2-B |
| `CREATE` | `connection` | новый оптический линк OM4 35 м, порты Te1/0/50 ↔ Te1/0/50 |
| `UPDATE` | `power_node` (INPUT) | `rated_current_a`: 32 → 50, `max_load_w`: 20000 → 30000 |
| `MOVE` | `rack_mount` | перенос SW-ACCESS-02 из R1 U40 в R2 U40 |
| `DELETE` | `ci` | вывод из эксплуатации старого UPS (в `RETIRED`, не физическое удаление) |
| `CONNECT` / `DISCONNECT` | `connection`, `power_link` | перекоммутация |

Свойства:

- у элементов есть порядок и зависимости (`depends_on`) — применение идёт в топологическом порядке;
- каждый элемент имеет статус применения (`PENDING/APPLIED/SKIPPED/FAILED`) и ссылку на созданную сущность;
- элементы могут быть сгенерированы автоматически из сценария (например, `power_scenario` порождает узлы и связи питания) или добавлены вручную;
- до применения ничего не попадает в рабочую модель, кроме объектов со статусом `PLANNED`, если пользователь явно попросил их «зарезервировать» (например, занять место в стойке).

### 7.1 Gap analysis

Автоматически вычисляемая разница CURRENT ↔ TARGET:

| Категория | Пример вывода |
|---|---|
| Мощность | «Дефицит 0.5 кВт по расчётной нагрузке; с нормативным запасом 20% требуется 25.6 кВт» |
| Место | «В стойке R2 требуется 7U, свободно 12U — достаточно» |
| Порты | «Требуется 4 порта SFP+ на SW-CORE-01, свободно 2 — дефицит 2 порта» |
| Вес | «Нагрузка на стойку R2: 480 кг из 800 кг» |
| Адресация | «Требуется 6 адресов в VLAN 20 (10.20.0.0/24), свободно 118» |
| Резервирование | «СХД планируется с одним вводом — нарушение политики A/B» |

Gap analysis — не текст, а набор проверок в `domain/states/gap_rules.py`, каждая возвращает статус (OK / WARNING / BLOCKER), число и объяснение. Проект с блокерами нельзя перевести в статус реализации без явного обоснования.

### 7.2 Применение

`POST /projects/{id}/planned-changes/{pid}/apply` — одна транзакция:

1. Проверить, что все элементы валидны относительно **текущей** (а не снимочной) модели; при расхождении — отчёт о конфликтах, применение не начинается.
2. Применить элементы в порядке зависимостей.
3. Записать аудит: каждая правка помечается `change_id` и `planned_change_id`.
4. Зафиксировать новый снимок состояния (`AFTER`).
5. Перевести `planned_change` в `APPLIED`, закрыть связанные `change`.
6. Запустить пересчёт: питание, поиск, кэш связей.

Откат: элементы содержат прежние значения, поэтому возможна генерация обратного набора операций (`rollback plan`) — он же используется в `change.rollback_md`.

## 8. Сквозной сценарий: «Увеличение вводной электрической мощности серверной»

Ниже — как 16 шагов из постановки ложатся на модель.

| Шаг | Действие в системе | Сущности |
|---|---|---|
| 1. Зафиксировать текущее состояние | Кнопка «Снять срез» в проекте: область = Серверная 205 | `state_snapshot` |
| 2. Собрать существующие нагрузки | Автоматически из модели питания; недостающие значения помечаются как дефекты данных | `power_node`, `power_node_computed` |
| 3. Определить текущий резерв | Расчёт: ввод 20 кВт − расчётная 16.8 кВт = 3.2 кВт | калькулятор мощности |
| 4. Добавить планируемое оборудование | Позиции сценария: 2 сервера, 1 СХД, 2 коммутатора, 1 UPS | `power_scenario_item` |
| 5. Рассчитать будущую нагрузку | Тот же калькулятор на модифицированном графе: 20.5 кВт | `power_scenario` |
| 6. Определить дефицит | −0.5 кВт к вводу; 5.6 кВт с нормативным запасом | gap analysis |
| 7. Сформировать целевую архитектуру | Новый ввод 3×50 А, новый UPS, новые PDU, размещение в R2 | `change_item[]` |
| 8. Определить необходимые изменения | Автогенерация списка изменений из целевого состояния | `planned_change`, `change` |
| 9. Создать план работ | Шаблон проекта разворачивается в этапы и задачи с зависимостями | `phase`, `task`, `task_dependency` |
| 10. Сформировать схемы | Однолинейная схема TARGET из DAG питания; схема стойки R2 после изменений | `diagram`, экспорт SVG/PDF |
| 11. Приложить техдокументацию | ТУ, расчёт нагрузок, спецификация, схемы | `document`, `document_version`, `file_object` |
| 12. Пакет документов для УК | Отчёт-комплект: расчёт + схемы + заявка; один PDF | `report_run`, `document` |
| 13. Вести согласование | Этапы согласования с внешней стороной, сроки, ответы | `change_approval` (`external_party = «УК»`), задачи-напоминания |
| 14. Зафиксировать результат | Полученные ТУ/разрешение как документ, привязанный к проекту | `document_link` |
| 15. Реализовать изменения | Работы выполняются как задачи; каждое физическое изменение — `change` с окном и rollback | `task`, `change`, `maintenance_window` |
| 16. Обновить модель | Применение `planned_change` → новая мощность ввода, новые узлы, новые связи, новый снимок | `apply`, `state_snapshot(AFTER)` |

Результат: проект закрыт, модель инфраструктуры соответствует реальности, история изменений содержит связь «объект изменён в рамках проекта PWR / изменения CHG-0031», а расчёт нагрузки пересчитан на новых данных.

## 9. Здоровье проекта (прозрачные правила)

Статус здоровья вычисляется правилами в `domain/projects/health.py`, каждое правило возвращает вклад и объяснение:

| Правило | Условие | Эффект |
|---|---|---|
| Просроченные задачи | есть задачи с `due_date < today` и статусом не финальным | AT_RISK; ≥ 5 или критический путь → DELAYED |
| Веха под угрозой | до вехи ≤ 7 дней, прогресс связанных задач < 70% | AT_RISK |
| Критический путь нарушен | задача на критическом пути просрочена | DELAYED |
| Блокирующие зависимости | задача `BLOCKED` дольше 3 дней | AT_RISK |
| Ресурс перегружен | исполнитель критической задачи загружен > 120% | AT_RISK |
| Блокеры gap analysis | есть BLOCKER (дефицит мощности/места/портов) | DELAYED |
| Бюджет | факт > плана на 10% | AT_RISK |
| Нет активности | нет изменений по проекту > 14 дней при статусе IN_PROGRESS | AT_RISK |

Итог — `ON_TRACK` / `AT_RISK` / `DELAYED` со списком причин. Никаких эвристик «на глаз»: каждое значение кликабельно и раскрывается в список объектов, которые его вызвали.

## 10. Шаблоны проектов

`project_template` хранит структуру: этапы, типовые задачи с зависимостями и оценками, вехи, чек-листы, перечень обязательных документов.

Предустановленные шаблоны:

| Шаблон | Состав |
|---|---|
| Увеличение электрической мощности | Обследование → расчёт → ТУ → согласование с УК → закупка → монтаж → испытания → ввод → обновление модели |
| Модернизация серверной | Аудит → проект → закупка → монтаж стоек → перенос оборудования → сеть → питание → тестирование |
| Замена коммутатора доступа | Подготовка конфигурации → окно работ → перекоммутация → проверка → вывод старого |
| Внедрение сервиса | Требования → архитектура → инфраструктура → установка → интеграция → документация → передача в эксплуатацию |
| Плановое ТО | Подготовка → уведомление → окно → работы → проверка → отчёт |

Шаблон может включать заготовку `planned_change` (например, «новый сервер: CI + размещение + питание + линк»), что резко сокращает ручной ввод.

## 11. Задачи: универсальность и связность

Задача связана с инфраструктурой через `task_ci` с ролью: «объект работ», «затронут», «источник проблемы». Это даёт:

- в карточке объекта — список всех работ по нему за всю историю;
- при планировании окна — автоматический расчёт затронутых сервисов;
- в отчёте «работы за период» — разрез по объектам, а не только по людям.

Учёт времени (`time_entry`) ведётся по датам, что позволяет строить загрузку сотрудников по дням недели и сравнивать оценку с фактом.

Повторяющиеся работы (`recurrence`) порождают новые экземпляры задач по расписанию — регламентные проверки (резервные копии, осмотр серверной, проверка UPS) живут в системе как плановые работы с историей выполнения.
