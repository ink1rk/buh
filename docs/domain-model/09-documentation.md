# 09 — Documentation (база знаний)

## 1. Чем это отличается от Wiki

| Wiki | Документация в ITMS |
|---|---|
| Страница живёт сама по себе | Документ привязан к объектам: сервисам, оборудованию, проектам, изменениям |
| Нет владельца | У документа есть автор, владелец и срок пересмотра |
| Версии как история правок | Версии как выпуски: номер, статус, утверждение, файл |
| Поиск по тексту | Поиск по тексту + по связанным объектам + по тегам и типу |
| Актуальность не контролируется | Просроченные пересмотры попадают в дашборд и отчёты |

Правило: **любой значимый объект инфраструктуры должен иметь документацию, и система показывает, у каких объектов её нет.**

## 2. Структура

```
document
  ├─ code            DOC-0042
  ├─ title           «Регламент резервного копирования»
  ├─ doc_type        REGULATION | INSTRUCTION | POLICY | STANDARD |
  │                  ARCHITECTURE | OPERATIONS | PROJECT | DIAGRAM | TEMPLATE | OTHER
  ├─ status          DRAFT → IN_REVIEW → APPROVED → OBSOLETE (→ ARCHIVED)
  ├─ folder          иерархия папок базы знаний
  ├─ author / owner  сотрудники
  ├─ tags[]          свободные метки
  ├─ review_period_months / review_due_on
  ├─ current_version_id
  ├─ document_version[]   неизменяемые версии
  └─ document_link[]      связи с объектами
```

### 2.1 Типы документов

Категории из постановки отображаются в `doc_type`: регламенты, инструкции, политики, стандарты, архитектурная документация, эксплуатационная документация, проектная документация, схемы, шаблоны, прочее.

Тип определяет: обязательные поля, необходимость утверждения, период пересмотра по умолчанию, место в структуре папок.

### 2.2 Два способа хранения тела

| Способ | Когда | Хранение |
|---|---|---|
| Markdown в системе | Инструкции, регламенты, заметки по эксплуатации | `document_version.body_md` |
| Приложенный файл | Внешние документы: PDF от подрядчика, DWG, XLSX-спецификация | `file_object` в MinIO + метаданные |

Оба варианта версионируются одинаково. Markdown предпочтителен: он ищется полнотекстово, отображается без загрузки, поддерживает diff между версиями и ссылки на объекты.

### 2.3 Ссылки на объекты внутри текста

В Markdown поддерживается синтаксис ссылок на CI: `[[ci:SRV-1C-01]]`, `[[service:1C]]`, `[[rack:R2]]`, `[[doc:DOC-0042]]`. При сохранении ссылки разбираются и материализуются в `document_link`. Результат: связь создаётся естественным образом в процессе написания, а не отдельной формой, и документ автоматически появляется в карточке объекта.

## 3. Версионирование

```
document_version(document_id, version_number, body_md | file_id,
                 summary, author_id, created_at)
```

Свойства:

- версии неизменяемы: правка создаёт новую версию, старая остаётся;
- `document.current_version_id` указывает на действующую;
- diff между любыми двумя версиями (для Markdown — построчный, для файлов — сравнение метаданных и контрольных сумм);
- откат = создание новой версии с телом старой (история не переписывается);
- каждая версия может иметь отдельное утверждение (`document_approval`): кто, когда, с каким комментарием.

## 4. Жизненный цикл и пересмотр

```
DRAFT ──► IN_REVIEW ──► APPROVED ──► OBSOLETE ──► ARCHIVED
  ▲            │             │
  └────────────┘             └── по истечении review_due_on → задача на пересмотр
```

Механика контроля актуальности:

1. У документа есть `review_period_months` (по типу: политики — 12, инструкции — 24, архитектура — 12).
2. При утверждении версии вычисляется `review_due_on`.
3. Фоновая задача формирует уведомления и создаёт задачу типа `TASK` владельцу за N дней до срока.
4. Отчёт «документы, требующие пересмотра» — один из системных отчётов; просроченные попадают на дашборд.

Это прямо закрывает требование §22 отчётности («документы, требующие пересмотра») и делает базу знаний живой.

## 5. Связи документа

`document_link(document_id, entity_type, entity_id, link_role)` связывает документ с любой сущностью:

| Связь | Пример |
|---|---|
| Документ ↔ CI | Паспорт сервера, инструкция по обслуживанию UPS |
| Документ ↔ сервис | Регламент восстановления сервиса «1С», SLA |
| Документ ↔ проект | ТЗ, спецификация, акты, переписка с УК |
| Документ ↔ изменение | План работ, rollback, акт выполненных работ |
| Документ ↔ локация | План помещения, схема электрощита |
| Документ ↔ задача | Инструкция, приложенная к плановой работе |

`link_role` уточняет характер: «схема», «инструкция», «акт», «спецификация», «согласование».

Обратная навигация обязательна: в карточке любого объекта есть блок «Документация» с этими же записями.

## 6. Схемы как документы

Схема (`diagram`) — живой объект, но у неё есть **выпуски**: экспорт в PDF/SVG сохраняется как версия документа типа `DIAGRAM`. Это даёт:

- зафиксированную схему «на дату» для согласования и печати;
- сравнение «как было спроектировано» и «как есть сейчас»;
- участие схем в общем контуре пересмотра документации.

---

## 7. Файлы

`file_object`: bucket, ключ, имя, MIME, размер, sha256, кто загрузил, к какой сущности относится.

Правила:
- физическое хранение — MinIO; БД хранит только метаданные;
- дедупликация по `sha256` (один и тот же файл, приложенный дважды, занимает место один раз);
- отдача — через временные подписанные ссылки, а не прямым путём;
- загрузка проверяет MIME и расширение по белому списку, имя санируется, исполняемые типы запрещены;
- предпросмотр в интерфейсе: PDF, изображения, Markdown, текст, CSV.

---

## 8. Поиск по документации

Документы индексируются в общем `search_index`: заголовок (вес A), теги и тип (B), тело (C/D). В результатах поиска документ показывается вместе со связанными объектами — это соответствует требованию «поиск должен показывать связанные объекты».

Дополнительные фильтры: по типу, статусу, владельцу, папке, тегам, дате пересмотра, наличию связей.

---

## 9. Шаблоны документов

`doc_type = TEMPLATE` + признак шаблона. Создание документа из шаблона подставляет структуру и обязательные разделы. Предустановленные шаблоны:

| Шаблон | Разделы |
|---|---|
| Паспорт сервиса | Назначение, владельцы, зависимости, SLA, восстановление, контакты |
| Регламент эксплуатации | Область, периодичность работ, процедуры, ответственные, контроль |
| План работ (change) | Цель, объекты, этапы, окно, проверка, rollback, уведомления |
| Инструкция по восстановлению | Предусловия, шаги, проверка, эскалация |
| Проектная документация | Текущее состояние, целевое, расчёты, спецификация, схемы, этапы |
| Отчёт о работах | Что сделано, отклонения, затраты, результат |

---

## 10. Что не делается в первой версии

- Полноценный WYSIWYG-редактор: используется Markdown с предпросмотром и вставкой изображений (проще, надёжнее, диффится).
- Совместное редактирование в реальном времени.
- Полнотекстовый поиск внутри вложенных PDF/DOCX (индексируются только метаданные; извлечение текста — кандидат на следующую фазу).
- Электронная подпись документов.
