# 10 — IT Operations: изменения, инциденты, плановые работы

## 1. Общая идея

Эксплуатация — это то, что происходит с инфраструктурой каждый день. В системе она представлена четырьмя связанными процессами:

```
    инцидент ──► проблема ──► изменение ──► обновление модели
       │                         ▲
       └──► плановая работа ─────┘
```

Все четыре используют универсальную задачу (`task` с `task_type`) как носитель работы и связаны с объектами (`task_ci`, `change_ci`) — поэтому история каждого объекта содержит и аварии, и плановые работы, и изменения.

---

## 2. Change Management

### 2.1 Зачем отдельная сущность

Изменение — не задача. У него есть причина, риск, окно, план отката, согласование, результат и **перечень затронутых объектов**. Изменение отвечает на вопрос «почему объект стал таким» спустя год.

```
change
  ├─ code                CHG-0031
  ├─ title / description / reason
  ├─ change_kind         STANDARD | NORMAL | EMERGENCY
  ├─ status              DRAFT → SUBMITTED → APPROVED → SCHEDULED →
  │                      IN_PROGRESS → IMPLEMENTED → VERIFIED → CLOSED
  │                      (ветви: REJECTED, ROLLED_BACK, FAILED)
  ├─ risk_level          LOW | MEDIUM | HIGH | CRITICAL
  ├─ initiator / implementer
  ├─ planned_window / actual_window   (tstzrange)
  ├─ plan_md / rollback_md / validation_md / result_md
  ├─ outcome             SUCCESS | PARTIAL | FAILED | ROLLED_BACK
  ├─ project_id          если изменение — часть проекта
  ├─ planned_change_id   если изменение применяет целевое состояние
  ├─ change_ci[]         затронутые объекты + характер воздействия
  ├─ change_approval[]   согласования (в т.ч. внешние стороны)
  └─ task[]              работы по реализации
```

### 2.2 Типы изменений и глубина процесса

| Тип | Согласование | Пример |
|---|---|---|
| `STANDARD` | Не требуется (предодобрено) | Замена патч-корда, добавление правила мониторинга |
| `NORMAL` | Требуется | Замена коммутатора, изменение схемы питания, обновление прошивки ядра |
| `EMERGENCY` | Постфактум | Аварийное восстановление |

Обязательные условия перехода:

- в `SUBMITTED` — заполнены `plan_md`, `rollback_md`, перечень `change_ci`;
- в `SCHEDULED` — назначено окно и исполнитель;
- в `IMPLEMENTED` — заполнен `result_md` и `outcome`;
- в `CLOSED` — проверка (`validation_md`) и, если изменение связано с `planned_change`, применение целевого состояния к модели.

### 2.3 Анализ влияния перед работами

При добавлении объектов в `change_ci` система автоматически вычисляет влияние (`impact_analysis`, см. `05-infrastructure-model.md`, §8):

- какие сервисы затрагиваются и их критичность;
- есть ли резерв (кластер, второй линк, сторона B питания);
- прогноз простоя: `NONE` / `DEGRADED` / `OUTAGE`;
- рекомендованное окно (пересечение нерабочих часов затронутых сервисов);
- кого уведомить (владельцы сервисов, ответственные за объекты).

Это превращает планирование работ из «вроде ничего не упадёт» в расчёт по модели.

### 2.4 След в истории

Каждая правка модели, выполненная в рамках изменения, помечается `audit_log.change_id`. В карточке объекта история выглядит так:

```
22.09.2026  Кирилл   статус: ACTIVE → MAINTENANCE        по CHG-0031
22.09.2026  Кирилл   стойка: R1 U20 → R2 U14             по CHG-0031
22.09.2026  Кирилл   питание: PDU R1-A → PDU R2-A        по CHG-0031
23.09.2026  Кирилл   статус: MAINTENANCE → ACTIVE        по CHG-0031
```

## 3. Инциденты

`incident` — расширение `task` (`task_type = INCIDENT`).

| Поле | Назначение |
|---|---|
| `service_id` | Затронутый сервис |
| `severity` | Влияние: LOW / MEDIUM / HIGH / CRITICAL |
| `detected_at`, `resolved_at`, `downtime_minutes` | Хронология и расчёт простоя |
| `root_cause` | Причина |
| `problem_id` | Связь с проблемой |
| `task_ci[]` | Задействованные объекты |

Жизненный цикл: `NEW → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED` (+ `REOPENED`).

**SLA-таймеры** (`sla_timer`): при создании инцидента по сервису с SLA запускаются таймеры реакции и решения; при нарушении ставится флаг `breached`, инцидент подсвечивается, событие попадает в отчёт. Таймеры учитывают часы обслуживания (`sla.service_hours`): для 8×5 ночное время не тикает.

Инциденты не являются HelpDesk-порталом: их заводит владелец системы или исполнитель, внешнего приёма обращений нет.

## 4. Проблемы

`problem` — расширение `task` (`task_type = PROBLEM`), группирует повторяющиеся инциденты.

Поля: корневая причина, обходное решение, ссылка на изменение с постоянным решением.

Практический смысл: три инцидента «пропадает сеть в кабинете 312» связываются с проблемой «деградация кабельной линии 312-2», которая закрывается изменением «замена линии». В карточке кабеля остаётся вся цепочка.

## 5. Плановые работы

`task_type = MAINTENANCE` + `maintenance_window`.

| Возможность | Механика |
|---|---|
| Регламентные работы | `recurrence`: еженедельная проверка бэкапов, ежемесячный осмотр серверной, ежеквартальный тест UPS |
| Окно работ | `maintenance_window.window_range` (tstzrange), пересечения окон проверяются GiST-индексом |
| Затронутые сервисы | Из `task_ci` + анализ влияния |
| Уведомления | За `notify_before_hours` до начала |
| Отчётность | Выполненные/пропущенные регламентные работы за период |

Календарь эксплуатации показывает окна, дедлайны задач и вехи проектов на одной шкале — это и есть «ближайшие работы» на дашборде.

## 6. Управление ИТ-отделом

Требование §19 реализуется данными, а не отдельным модулем.

### 6.1 Карточка сотрудника

- ФИО, должность, отдел, линия поддержки (1/2/3), специализации, контакты, активность;
- назначенные задачи (по статусам и срокам);
- проекты, в которых участвует;
- зоны ответственности (`responsibility_area`) → развёрнутый список объектов;
- объекты, где он владелец или ответственный;
- выполненные работы за период и затраченное время;
- загрузка по дням.

### 6.2 Загрузка

Расчёт: для каждого дня суммируются оценки (`estimate_min`) активных задач, распределённые по диапазону `start_date..due_date`, плюс окна плановых работ. Сравнение с дневной ёмкостью (`weekly_capacity_hours / 5`).

Отображение: недельная сетка Пн–Пт по сотрудникам, цвет — степень загрузки, перегруз выделяется. Клик по ячейке — список работ этого дня.

Ограничение метода описано честно: оценка равномерно размазывается по интервалу задачи, поэтому загрузка — планировочный ориентир, а не табель. Фактические трудозатраты берутся из `time_entry`.

### 6.3 Контроль

| Показатель | Источник |
|---|---|
| Просрочки по сотрудникам | `task.due_date < today AND status NOT IN (DONE, CANCELLED)` |
| Текущие задачи | `status IN (IN_PROGRESS, REVIEW)` |
| Выполнено за период | `completed_at BETWEEN …` |
| Среднее время выполнения | `completed_at − created_at` по типам задач |
| Соблюдение SLA | `sla_timer.breached` по исполнителям |
| Регламентные работы | Выполненные экземпляры `recurrence` против запланированных |

## 7. Дашборд руководителя

Дашборд — рабочий инструмент, каждый блок кликабелен и ведёт в отфильтрованный список.

| Блок | Содержание | Правило наполнения |
|---|---|---|
| Оперативная сводка | 1–2 строки: сколько активных инцидентов, просрочек, работ сегодня, критичных предупреждений | Агрегаты |
| Мои задачи | Сегодня, просрочено, на неделю | `assignee = owner` |
| Активные инциденты | Открытые, с SLA-таймером и оставшимся временем | `incident.status != CLOSED` |
| Изменения | На согласовании, запланированные на ближайшие дни, в работе | `change.status` |
| Плановые работы | Окна на ближайшие 7 дней | `maintenance_window` |
| Проекты | Прогресс, здоровье, ближайшая веха, просрочки | `project` + health-правила |
| Загрузка сотрудников | Мини-сетка недели | Расчёт загрузки |
| Состояние инфраструктуры | Объекты в статусах `DEGRADED`/`MAINTENANCE`, стойки и вводы с загрузкой > 80%, нарушения резервирования | CMDB + расчёты питания |
| Критические объекты | CI с `criticality = CRITICAL` и их состояние | CMDB |
| Сроки | Истекающие сертификаты, домены, гарантии, документы к пересмотру | `renewal_watch` |
| Качество модели | Объекты без владельца/документации/размещения | Проверки качества |
| Уведомления | Непрочитанные важные события | `notification` |

Дашборд настраиваемый: набор и порядок блоков сохраняется в профиле. Никаких декоративных виджетов — каждый блок отвечает на вопрос «что мне сейчас сделать».

## 8. Уведомления

Внутренние уведомления (`notification`) для владельца системы:

| Событие | Когда |
|---|---|
| Новый инцидент / повышение severity | немедленно |
| Приближение или нарушение SLA | по таймеру |
| Изменение требует согласования / согласовано / отклонено | по переходу статуса |
| Окно работ начинается | за `notify_before_hours` |
| Задача просрочена | утренняя сводка |
| Сертификат/домен/гарантия истекает | за 60/30/7 дней |
| Документ требует пересмотра | за 30 дней |
| Перегрузка по питанию (расчёт > 80% лимита) | при пересчёте |
| Дефект качества модели (новый объект без владельца) | утренняя сводка |

Дедупликация по `dedupe_key` исключает повторные уведомления об одном и том же. Внешние каналы (Telegram, email) в текущем этапе не реализуются — архитектурно это подписчики того же потока событий.

## 9. Что не реализуется сейчас

- Портал самообслуживания и приём обращений от пользователей.
- Автоматическое создание инцидентов из мониторинга (Phase 8+, Integration Layer).
- Полная реализация ITIL-процессов (CAB, release management, service catalog для бизнеса).
- Учёт стоимости простоя и биллинг сервисов.
