# 02 — Доменная модель

## 1. Ядро модели: Configuration Item (CI)

Любой значимый объект ИТ-ландшафта — это **CI**. Здание, помещение, стойка, сервер, коммутатор, порт-панель, ИБП, автомат, виртуальная машина, приложение, база данных, сервис, домен, сертификат — всё это CI разных типов.

```
                       ┌──────────────────────────┐
                       │            ci            │  ← общая часть: идентичность,
                       │  id, ci_type, name, code │     владение, статус, аудит,
                       │  status, criticality     │     связи, документы, задачи
                       │  owner_id, responsible_id│
                       │  location_id, attributes │
                       └────────────┬─────────────┘
         ┌──────────────┬───────────┼────────────┬───────────────┬────────────┐
         ▼              ▼           ▼            ▼               ▼            ▼
   ┌───────────┐  ┌──────────┐ ┌─────────┐ ┌──────────┐  ┌────────────┐ ┌──────────┐
   │  device   │  │   rack   │ │ service │ │application│ │ power_node │ │ location │
   │ hardware  │  │ 19", U   │ │ SLA,    │ │ VM, DB,   │ │ UPS, PDU,  │ │ building │
   │ модель,   │  │ вес,     │ │ критич- │ │ кластер,  │ │ автомат,   │ │ floor,   │
   │ S/N, PSU  │  │ питание  │ │ ность   │ │ ОС        │ │ линия      │ │ room,rack│
   └───────────┘  └──────────┘ └─────────┘ └──────────┘  └────────────┘ └──────────┘
```

Реализация — **joined-table inheritance**: общая таблица `ci` + таблица-расширение на подтип с тем же первичным ключом. Не «одна большая таблица со всеми полями» и не «независимые таблицы».

### 1.1 Что даёт единый базовый тип

Каждая из этих возможностей реализуется **один раз** и работает для всех типов объектов:

| Возможность | Механика |
|---|---|
| Связи между любыми объектами | `ci_relation(source_ci_id, target_ci_id, rel_type)` |
| Привязка документов | `document_link(document_id, ci_id)` |
| Привязка задач | `task_ci(task_id, ci_id, role)` |
| Привязка изменений | `change_ci(change_id, ci_id, impact)` |
| История изменений | `audit_log` + `audit_change` по `entity_type='ci'` |
| Комментарии и вложения | `comment(ci_id)`, `file_object` |
| Поиск | одна строка в `search_index` на CI |
| Владелец и ответственный | поля в `ci`, отчёт «объекты без владельца» — один запрос |
| Жизненный цикл | общий набор статусов |
| Произвольные поля | `ci.attributes jsonb` + реестр `custom_field` |

Без базового типа каждую из этих функций пришлось бы реализовывать для 20+ таблиц.

### 1.2 Поля базового CI

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid | Идентификатор; uuid, а не serial — объекты создаются в импортах и сценариях до записи в БД |
| `ci_type` | enum | Дискриминатор подтипа (`DEVICE`, `RACK`, `SERVICE`, `APPLICATION`, `VM`, `CLUSTER`, `DATABASE`, `POWER_NODE`, `LOCATION`, `DOMAIN`, `CERTIFICATE`, `STORAGE`, `CIRCUIT`, …) |
| `name` | text | Человекочитаемое имя (`SW-CORE-01`) |
| `code` | text, uniq | Инвентарный/системный код, уникален в системе |
| `status` | enum | `PLANNED`, `ORDERED`, `IN_STOCK`, `ACTIVE`, `DEGRADED`, `MAINTENANCE`, `RESERVED`, `DECOMMISSIONING`, `RETIRED` |
| `criticality` | enum | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` — используется в дашборде и отчётах |
| `environment` | enum | `PROD`, `TEST`, `DEV`, `DR` |
| `owner_id` | fk employee | Владелец (отвечает за объект как за актив) |
| `responsible_id` | fk employee | Ответственный за эксплуатацию |
| `location_id` | fk location | Где физически находится (для логических CI — nullable) |
| `description` | text | Описание |
| `attributes` | jsonb | Произвольные поля по реестру `custom_field` |
| `source_system`, `external_id`, `is_managed_externally`, `last_synced_at` | — | Происхождение данных (Integration Layer) |
| `valid_from`, `valid_to` | date | Ввод в эксплуатацию / вывод |
| `version` | int | Оптимистическая блокировка |
| `created_at`, `updated_at`, `created_by`, `updated_by`, `deleted_at` | — | Служебные |

**Политика удаления.** Физическое удаление CI запрещено на уровне API: на объект ссылаются история, документы, завершённые проекты и изменения.

| Сценарий | Действие | Результат |
|---|---|---|
| Оборудование выведено из эксплуатации | Перевод в `DECOMMISSIONING` → `RETIRED` | Объект остаётся в модели, исчезает из рабочих списков, доступен в истории и отчётах за период |
| Объект больше не нужен в оперативной работе | Архивирование (`archived_at`) | Скрыт из списков и поиска по умолчанию, восстанавливается одним действием |
| Ошибочно заведённый объект без истории | Мягкое удаление (`deleted_at`) | Доступно только владельцу и только если по объекту нет изменений, задач и документов |
| Физическое удаление | Недоступно через API | Возможно лишь прямой операцией в БД при обслуживании, с фиксацией в журнале |

Для критических инфраструктурных объектов (`criticality = CRITICAL`, а также всё, что участвует в электрической или сетевой топологии) доступны только `RETIRED` и архивирование — мягкое удаление заблокировано.

### 1.3 Типы CI и их расширения

| `ci_type` | Таблица-расширение | Ключевые поля расширения |
|---|---|---|
| `LOCATION` | `location` | `location_type` (ORG/SITE/BUILDING/FLOOR/ROOM/ZONE), `parent_id`, `path`, `area_m2`, план помещения |
| `RACK` | `rack` | `u_height`, `width_in`, `depth_mm`, `max_weight_kg`, `max_power_w`, `numbering_desc`, координаты на плане |
| `DEVICE` | `device` | `model_id`, `serial_number`, `asset_tag`, `hostname`, `mgmt_ip`, `firmware`, `device_role`, `psu_count`, `power_nameplate_w`, `power_max_w`, `warranty_until` |
| `VM` | `virtual_machine` | `vcpu`, `ram_mb`, `disk_gb`, `guest_os`, `hypervisor_host_id`, `cluster_id` |
| `CLUSTER` | `cluster` | `cluster_type`, `node_count`, `ha_policy` |
| `APPLICATION` | `application` | `app_type`, `vendor`, `version`, `runtime`, `url` |
| `DATABASE` | `database_instance` | `engine`, `version`, `port`, `size_gb`, `backup_policy_id` |
| `SERVICE` | `service` | `category`, `sla_id`, `business_owner_id`, `service_hours`, `rto_min`, `rpo_min` |
| `STORAGE` | `storage_system` | `capacity_tb`, `used_tb`, `protocol`, `raid` |
| `POWER_NODE` | `power_node` | `node_type` (INPUT/PANEL/BREAKER/LINE/UPS/PDU/OUTLET/PSU), электрические параметры |
| `DOMAIN` | `domain` | `registrar_id`, `expires_at`, `dns_provider` |
| `CERTIFICATE` | `certificate` | `cn`, `sans`, `issuer`, `valid_to`, `key_type` |
| `CIRCUIT` | `circuit` | внешний канал связи: провайдер, тип, полоса, SLA |

Новый тип объекта добавляется как новое значение `ci_type` + таблица-расширение. Связи, документы, задачи, аудит и поиск начинают работать для него автоматически.

### 1.4 Что намеренно НЕ является CI

`interface` (порт), `connection` (кабель), `ip_address`, `vlan`, `prefix`, `rack_mount`, `power_link` — не CI, а **элементы топологии**. Причины:

- их тысячи на объект, базовые поля CI (владелец, критичность, локация) для них избыточны;
- у них жёсткие специфичные ограничения (уникальность порта в устройстве, непересечение U, один активный кабель на порт);
- они всегда принадлежат конкретному CI и не существуют отдельно.

При этом они участвуют в связях и истории через владеющий CI и имеют собственные записи аудита.

## 2. Связи: два уровня

### 2.1 Уровень 1 — типизированные топологические таблицы

Физика и точные инженерные связи моделируются отдельными таблицами, потому что им нужны атрибуты и ограничения:

| Связь | Таблица | Что обеспечивает |
|---|---|---|
| Порт ↔ порт (кабель) | `connection` | Категория, длина, трасса, маркировка, состояние; один активный кабель на интерфейс |
| Устройство ↔ стойка (U) | `rack_mount` | Позиция U, фасад, глубина, вес; запрет перекрытия диапазонов U |
| Питание: узел → узел | `power_link` | Фаза, номинал, сторона A/B; DAG без циклов |
| IP ↔ интерфейс | `ip_address` | Уникальность адреса в VRF, принадлежность подсети |
| Интерфейс ↔ VLAN | `interface_vlan` | Access/trunk, native VLAN |
| Объект ↔ план помещения | `floorplan_item` | Координаты, поворот, габариты |

### 2.2 Уровень 2 — универсальный граф `ci_relation`

Логические зависимости хранятся в одной таблице рёбер:

```
ci_relation(id, source_ci_id, target_ci_id, rel_type, attributes jsonb,
            criticality, description, valid_from, valid_to, created_by)
```

Типы связей (`rel_type`):

| Тип | Направление (source → target) | Пример |
|---|---|---|
| `DEPENDS_ON` | зависит от | Сервис «1С» → SQL-сервер |
| `RUNS_ON` | выполняется на | VM → гипервизор; приложение → VM |
| `MEMBER_OF` | входит в | Хост → кластер |
| `PART_OF` | часть | Модуль → шасси |
| `CONNECTED_TO` | логическая связность | Сервис → внешний канал |
| `USES_STORAGE` | использует хранилище | VM → СХД |
| `BACKED_UP_BY` | резервируется | БД → Veeam-job (будущая интеграция) |
| `REPLICATES_TO` | реплицируется в | БД → DR-площадка |
| `MANAGES` | управляет | Контроллер → точки доступа |
| `SERVES` | обслуживает | Сервис → отдел |
| `RELATES_TO` | произвольная связь | Любая пара |

Правила:

1. Связь направленная; обратный обход выполняется тем же запросом (`source_ci_id = :id OR target_ci_id = :id`), в UI показывается как «зависит от» / «от него зависят».
2. Пара `(source, target, rel_type)` уникальна.
3. Для `DEPENDS_ON` запрещены циклы — проверка рекурсивным CTE при вставке.
4. У связи есть срок действия (`valid_from`/`valid_to`) — история зависимостей сохраняется.
5. `criticality` у связи позволяет отличать «сервис не работает без этого» от «деградирует».
6. **Электропитание в `ci_relation` не выражается** — см. §2.4.

### 2.3 Почему не всё в `ci_relation`

Если кабель — это строка в `ci_relation` с атрибутами в `jsonb`, то теряются: уникальность порта, проверка категории, расчёт длины трассы, индексы по маркировке, отчёт «свободные порты». Разделение на два уровня — осознанный компромисс между строгостью и гибкостью.

### 2.4 Электрика — только `power_link`, без дублирующей логической связи

Цепочка `Ввод → щит → автомат → линия → UPS → PDU → розетка → PSU → оборудование` является однозначной инженерной моделью и хранится **исключительно** в `power_node` + `power_link`.

Запрещено:

- значение `POWERED_BY` в перечислении `relation_type` (его нет в типе и не будет добавлено);
- любые попытки описать питание строкой в `ci_relation` — валидация сервисного слоя отклоняет связь, если оба конца являются узлами питания.

Почему это принципиально. Два источника истины для электрики означают: расчёт нагрузки может использовать одну связь, а анализ отказа ветки — другую; при перекоммутации PDU обновится одна таблица и не обновится вторая; отчёт для управляющей компании будет построен по неполным данным. Электрическая модель требует фазы, номинала, тока, стороны питания и участия в расчёте — ничего из этого `ci_relation` не выражает и не должен.

Единственная разрешённая логическая связь рядом с электрикой — `DEPENDS_ON` от сервиса к узлу питания (например, «сервис зависит от ИБП-1» на уровне бизнес-зависимости). Она не участвует в расчётах нагрузки и не заменяет `power_link`.

## 3. Карточка объекта: обязательная проекция графа

Требование §30 задания реализуется как единый контракт: `GET /api/v1/ci/{id}/related` возвращает **все** связанные объекты, сгруппированные по смыслу. Для `SERVER-01`:

| Блок | Источник данных |
|---|---|
| Физическое размещение | `location` (цепочка Организация → Здание → Этаж → Помещение → Зона) |
| Стойка и U-позиция | `rack_mount` → `rack` |
| Виртуальные машины | `ci_relation RUNS_ON` (входящие) |
| Сервисы, которые зависят | `ci_relation DEPENDS_ON` (входящие, транзитивно) |
| Сетевые порты | `interface` устройства |
| Кабели | `connection` по интерфейсам + трассировка через патч-панели |
| IP-адреса и VLAN | `ip_address`, `interface_vlan` |
| Питание | `power_link` от `psu` вверх по DAG до ввода (PDU → UPS → автомат → щит → ввод) |
| Владелец / ответственный | `employee` |
| Документы | `document_link` |
| Проекты | `project_ci` |
| Задачи | `task_ci` |
| Изменения | `change_ci` |
| История | `audit_log` + `audit_change` |

Тот же контракт работает в обратную сторону: у документа есть список объектов, у проекта — затронутая инфраструктура, у сотрудника — зоны ответственности.

Глубина обхода параметризуется (`?depth=1..3`), запросы — рекурсивные CTE с ограничением глубины и количества узлов.

## 4. Люди и организация

```
organization ── department ── employee ──┬── owner_of: ci[]
                                          ├── responsible_for: ci[]
                                          ├── assignee_of: task[]
                                          ├── member_of: project[]
                                          └── responsibility_area[]
```

**Employee:** ФИО, должность, `support_line` (1st/2nd/3rd/none), специализация (массив тегов: сеть, серверы, 1С, СКУД…), контакты, статус активности, недельная ёмкость (часы), отдел.

**Зоны ответственности** (`responsibility_area`) — правило, а не ручной список: «все CI типа DEVICE в помещении Серверная-1», «все сервисы категории Бизнес-приложения». Хранится как именованный фильтр, разворачивается в список объектов запросом. Это даёт отчёт «у объекта нет ответственного» без ручного сопровождения таблиц.

**Контроль работы отдела** строится на данных, а не на отдельном модуле: загрузка = сумма оценок открытых задач по дням; просрочки = задачи с `due_date < today`; выполненные работы = задачи и изменения со статусом завершения за период.

## 5. Универсальная задача

Одна сущность `task` с дискриминатором `task_type`:

| Тип | Особенности |
|---|---|
| `TASK` | Базовая работа |
| `SUBTASK` | `parent_id` указывает на родителя |
| `INCIDENT` | Приоритет по влиянию, SLA-таймеры, связь с сервисом, признак «авария» |
| `PROBLEM` | Группирует инциденты, есть поле «корневая причина» |
| `REQUEST` | Заявка от сотрудника/отдела |
| `MAINTENANCE` | Плановая работа, окно проведения, повторяемость |
| `CHANGE_TASK` | Шаг реализации `change` |

Почему одна таблица: у всех типов одинаковые поля (исполнитель, сроки, оценка, факт, зависимости, связанные объекты, документы), одинаковые Kanban/список/календарь/Gantt и одинаковая история. Специфика — в необязательных полях и в правилах статусной модели на тип. Разные таблицы означали бы четыре реализации одного и того же.

Ключевые поля: `title`, `description`, `task_type`, `status`, `priority`, `assignee_id`, `reporter_id`, `project_id`, `phase_id`, `parent_id`, `change_id`, `service_id`, `start_date`, `due_date`, `estimate_min`, `spent_min`, `completed_at`, `recurrence_id`.

Связи задачи: `task_dependency` (BLOCKS / RELATES_TO), `task_ci` (затронутые объекты), `document_link`, `comment`, `file_object`, `time_entry`.

## 6. Статусные модели (жизненные циклы)

Статусы не произвольные строки: для каждого типа сущности определён граф переходов. Переходы проверяются в доменном слое.

**CI:**
```
PLANNED → ORDERED → IN_STOCK → ACTIVE ⇄ MAINTENANCE
                                  ↓            ↓
                              DEGRADED → DECOMMISSIONING → RETIRED
```

**Task:** `NEW → IN_PROGRESS → ON_HOLD | BLOCKED → REVIEW → DONE | CANCELLED`

**Incident:** `NEW → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED` (+ `REOPENED`)

**Change:** `DRAFT → SUBMITTED → APPROVED | REJECTED → SCHEDULED → IN_PROGRESS → IMPLEMENTED → VERIFIED → CLOSED` (+ `ROLLED_BACK`, `FAILED`)

**Project:** `DRAFT → PLANNING → IN_PROGRESS → ON_HOLD → COMPLETED | CANCELLED`

**Document:** `DRAFT → IN_REVIEW → APPROVED → OBSOLETE` (+ `ARCHIVED`)

Переходы, меняющие инфраструктуру (`Change: IMPLEMENTED`, `Project: COMPLETED`), запускают применение TARGET STATE к модели — см. `08-project-management.md`.

## 7. История изменений

Три уровня, каждый со своей ролью:

| Уровень | Что хранит | Назначение |
|---|---|---|
| `audit_log` + `audit_change` | Кто, что, когда, откуда, старое → новое по каждому полю | Юридическая история, требование §24 |
| `domain_event` / `outbox` | Факты предметной области (`ci.status_changed`) | Реакции системы, интеграции |
| Лента активности (view) | Человекочитаемая выжимка из аудита | UI: вкладка «История» у объекта |

**Что фиксируется:** создание, изменение любого поля, мягкое удаление, восстановление, добавление/удаление связи, перемещение в стойке, перекоммутация кабеля, изменение питания, смена статуса, изменение документа, участие в изменении (`change`).

**Формат записи:**

```
audit_log:    id, occurred_at, actor_id, actor_kind (user|system|import),
              request_id, entity_type, entity_id, action, comment, source,
              -- происхождение изменения (provenance):
              change_id, project_id, task_id, document_id, reason
audit_change: audit_log_id, field, old_value jsonb, new_value jsonb
```

### 7.1 Происхождение изменения (обязательный принцип)

Любое изменение инфраструктуры должно иметь происхождение: спустя год по любому параметру объекта нужно понять **кто, когда, почему и в рамках чего** его изменил.

```
SERVER-07
  power_nameplate_w: 650 → 850 Вт
        │
        ├── кто:      Кирилл, 22.09.2026 14:18
        ├── причина:  «замена БП на 850 Вт по результатам апгрейда»
        └── в рамках: проект PRJ-042 «Модернизация серверной»
                       ├── изменение CHG-0018
                       ├── задача    TASK-154
                       └── документ  DOC-0027 «Акт замены БП»
```

Механика:

1. Контекст происхождения (`change_id`, `project_id`, `task_id`, `document_id`, `reason`) передаётся через `contextvars` и заголовки запроса (`X-Change-Id`, `X-Project-Id`, `X-Task-Id`, `X-Reason`) и автоматически попадает в каждую запись `audit_log` внутри операции.
2. В интерфейсе это не поле формы, а **рабочий контекст**: если пользователь редактирует объект, открыв его из задачи или изменения, привязка проставляется сама; при прямой правке система предлагает указать причину.
3. Правки в рамках `change` со статусом `IN_PROGRESS` привязываются к нему автоматически.
4. Применение целевого состояния проекта (`planned_change.apply`) проставляет `project_id` и `change_id` всем порождённым правкам.
5. Для изменений, помеченных как критичные (статус, размещение, питание, владелец, вывод из эксплуатации), причина или ссылка на изменение **обязательна** — иначе операция отклоняется. Перечень критичных полей настраивается в справочнике.
6. Массовые операции и импорт записывают `actor_kind = IMPORT` и ссылку на `import_job`.

API: `GET /ci/{id}/provenance?field=power_nameplate_w` возвращает историю конкретного параметра с происхождением каждого значения; в карточке объекта это отображается рядом с полем.

Свойства:
- записи иммутабельны (нет UPDATE/DELETE в API; на уровне БД — отзыв прав на изменение);
- изменение в рамках `change` связывается с ним — в карточке объекта видно «изменено по CHG-14»;
- карточка любого объекта показывает историю единым запросом по `(entity_type, entity_id)`;
- для документов дополнительно есть полноценные версии (`document_version`) со снимком тела и diff.

## 8. Произвольные атрибуты

Реестр `custom_field(entity_type, ci_type, key, label, data_type, options, required, order)` + значения в `ci.attributes jsonb`.

Правила:
- поля, которые участвуют в расчётах, фильтрах по умолчанию или ограничениях, — **всегда колонки**, а не jsonb;
- jsonb — для специфики конкретного парка («инвентарный номер УК», «номер договора аренды стойки»);
- поиск по jsonb обеспечивается GIN-индексом, отображение — реестром полей.

## 10. Инварианты предметной области

Список правил, которые система обязана держать всегда (реализация — ограничения БД + доменные проверки):

1. Устройство не может занимать U, уже занятые другим устройством в той же стойке и на том же фасаде.
2. Устройство не может выходить за пределы стойки (`position_u + u_height - 1 ≤ rack.u_height`).
3. Интерфейс может иметь не более одного активного кабеля.
4. Кабель соединяет ровно два интерфейса, и они различны.
5. IP-адрес уникален в пределах VRF; адрес обязан принадлежать своей подсети.
6. Граф питания — DAG: цикл «PDU питает UPS, который питает этот PDU» невозможен.
7. Граф `DEPENDS_ON` — без циклов.
8. Дерево локаций — без циклов; `path` согласован с `parent_id`.
9. Задача не может зависеть сама от себя (в том числе транзитивно).
10. `code` CI уникален среди неудалённых объектов.
11. Нельзя перевести `Change` в `IMPLEMENTED`, если не заполнены план и rollback.
12. Нельзя закрыть проект с незавершёнными элементами TARGET STATE, кроме как с явным указанием причины.
