# 05 — Infrastructure Model (ядро системы)

Центральный модуль. Здесь описано, как система представляет физический и сетевой ландшафт и как из этого представления получаются ответы на инженерные вопросы.

## 1. Принцип моделирования

Три слоя, связанных между собой:

```
ЛОГИЧЕСКИЙ     сервисы, приложения, VM, БД, кластеры         «что работает»
    ↕ RUNS_ON / DEPENDS_ON
СЕТЕВОЙ        устройства, интерфейсы, кабели, VLAN, IP      «как связано»
    ↕ rack_mount / location
ФИЗИЧЕСКИЙ     здания, помещения, стойки, U, трассы          «где стоит»
    ↕ power_link
ЭЛЕКТРИЧЕСКИЙ  ввод, щит, автомат, UPS, PDU, розетка, PSU    «чем питается»
```

Каждый слой самостоятельно осмыслен, но объект принадлежит всем одновременно: сервер `SRV-1C-01` — это одновременно строка в `device`, размещение в `rack_mount`, набор `interface`, набор `psu`-узлов питания и цель зависимостей сервиса «1С».

## 2. Физическая иерархия

```
organization «ООО Компания»
 └─ SITE «Площадка Север»              location_type=SITE
     └─ BUILDING «Корпус А»            адрес, этажность
         └─ FLOOR «2 этаж»             план этажа
             └─ ROOM «Серверная 205»   площадь, план помещения
                 ├─ ZONE «Ряд 1»
                 │   ├─ RACK «R1»      42U, 600×1000, 800 кг, 7 кВт
                 │   └─ RACK «R2»
                 └─ ZONE «Электрощитовая»
                     └─ power_node PANEL «ЩС-1»
```

Свойства модели локаций:

- одна таблица `location` с типом узла; иерархия — `parent_id` + материализованный путь `path`;
- запрос «всё оборудование в корпусе А» = `WHERE location.path LIKE 'org/site-north/bld-a/%'` — один индексный скан;
- у каждого узла может быть план (`floorplan`), на плане размещаются объекты с координатами (`floorplan_item`): стойки, щиты, кабельные трассы, точки подключения, рабочие места;
- стойка — одновременно локация для оборудования и объект на плане помещения (поля `plan_x`, `plan_y`, `plan_rotation`).

**Точность координат.** План хранится в миллиметрах с масштабом `scale_px_per_m`; подложкой может быть загруженный чертёж (PDF/PNG в MinIO). Это даёт возможность измерять расстояния (например, длину кабельной трассы) прямо по плану.

## 3. Оборудование

### 3.1 Каталог моделей как основа расчётов

Габариты, вес и мощность хранятся не у экземпляра, а у **модели** (`device_model`). Экземпляр (`device`) может переопределить значение, если измерено фактически.

Зачем это критично:
- редактор стоек знает высоту в U и глубину до того, как устройство размещено;
- электрический расчёт берёт `power_draw_w` / `power_max_w` из модели, если у экземпляра нет измерения;
- планирование закупки («добавим 2 таких сервера») оперирует моделью, а не выдуманными числами;
- шаблон портов (`port_template`) автоматически создаёт интерфейсы при заведении устройства: `Gi1/0/1..48` + `Te1/0/49..52`.

### 3.2 Роли устройств

Одна таблица `device` с полем `device_role`: сервер, маршрутизатор, L3/L2-коммутатор, firewall, точка доступа, контроллер Wi-Fi, модем, патч-панель, сетевая розетка, СХД, KVM, ИБП, PDU, принтер, прочее.

Почему не отдельные таблицы на роль: набор полей идентичен на 95% (производитель, модель, S/N, hostname, mgmt IP, MAC, прошивка, размещение, владелец, статус, питание), а специфика умещается в `attributes` и связанные таблицы. Отдельные таблицы дали бы 12 почти одинаковых CRUD и 12 наборов джойнов в отчётах.

### 3.3 Пассивное оборудование

Патч-панели и сетевые розетки моделируются как устройства с интерфейсами, у которых:
- `panel_side = FRONT | REAR`;
- `paired_interface_id` связывает фронтальный порт с тыловым.

Это позволяет вести сквозную трассировку линка через пассивку (см. §5.3) — без этого «кабель от сервера» всегда обрывался бы на патч-панели.

## 4. Интерфейсы

Интерфейс — порт устройства. Хранимые поля: имя, номер/позиция, тип разъёма, среда, скорость, дуплекс, MAC, описание, назначение, административное и операционное состояние, PoE, MTU, принадлежность к LAG, сторона патч-панели и парный порт.

Дополнительно интерфейс связан с:
- IP-адресами (`ip_address.interface_id`), их может быть несколько;
- VLAN (`interface_vlan`: access / tagged / native);
- кабелем (`connection`, максимум один активный).

Логические интерфейсы (`VIRTUAL`, `LAG`, `VLAN_IF`) хранятся в той же таблице: у них нет кабеля, но есть адреса и VLAN. Это позволяет описывать SVI, bond'ы и туннели без отдельной сущности.

**Отчёт «свободные порты»** — прямое следствие модели:

```sql
SELECT d.hostname, count(*) FILTER (WHERE c.id IS NULL) AS free_ports
FROM interface i
JOIN device d ON d.id = i.ci_id
LEFT JOIN connection c
       ON (c.a_interface_id = i.id OR c.b_interface_id = i.id)
      AND c.status IN ('ACTIVE','RESERVED')
WHERE i.interface_type IN ('RJ45','SFP','SFP_PLUS')
GROUP BY d.hostname;
```

## 5. Соединения

### 5.1 Соединение — самостоятельная сущность

Кабель существует отдельно от портов, потому что у него есть собственные свойства и собственная история: тип, категория, длина, маркировка, трасса, дата монтажа, результат тестирования, состояние, участие в резервировании.

Пример из задания моделируется так:

```
device  SW-CORE-01
 └─ interface «Te1/0/49», type=SFP_PLUS, speed=10000, position=49
       │
       └─ connection  label «F-A2-14»
             medium   FIBER
             category OM4
             length_m 35.5
             route    «Лоток A2 → стояк 3 → Серверная 205»
             status   ACTIVE
             │
 └─ interface «Te1/0/49», type=SFP_PLUS, speed=10000
device  SW-ACCESS-02
```

### 5.2 Инварианты

1. Один активный кабель на интерфейс (частичный уникальный индекс).
2. Кабель соединяет два разных интерфейса.
3. Скорость линка не может превышать минимальную скорость портов — предупреждение, а не запрет (бывает осознанно).
4. Несовместимость среды (медный патч в SFP+ порт) — предупреждение с возможностью подтвердить.
5. Статусы `PLANNED` и `RESERVED` позволяют проектировать коммутацию до монтажа (используется в TARGET STATE проектов).

### 5.3 Сквозная трассировка линка

Физический путь «сервер → патч-панель → кросс → коммутатор» состоит из нескольких `connection`. Сквозной линк вычисляется обходом:

```
start: interface I0
loop:
  c ← активный connection у текущего интерфейса
  next ← противоположный конец c
  если владелец next — пассивное устройство и у next есть paired_interface_id:
      текущий ← paired_interface_id      (проходим панель насквозь)
      продолжаем
  иначе:
      конец пути: next — конечная точка
```

Результат — `link_path`: список сегментов, суммарная длина, список пройденных панелей, конечные устройства. Кэшируется в `link_path_computed`, инвалидация — по событию изменения любого сегмента.

Практическая ценность: на схеме показывается логический линк «SRV-01 ↔ SW-CORE-01», а в карточке — из каких физических кусков он состоит и где порвётся, если выдернуть патч-корд в кроссе.

### 5.4 Резервирование

Поля `is_redundant` и `redundancy_group` позволяют пометить два линка как пару. Система проверяет и показывает нарушения: «оба линка группы LAG-CORE проходят по одной трассе A2» или «резервный линк в статусе FAULTY».

## 6. Адресация: VLAN, подсети, IP

| Сущность | Роль |
|---|---|
| `vrf` | Пространство адресов (по умолчанию один `default`) |
| `vlan` | VID + имя + назначение, привязка к площадке |
| `prefix` | Подсеть `cidr`, шлюз, диапазон DHCP, связь с VLAN |
| `ip_address` | Конкретный адрес, привязка к интерфейсу или к объекту |

Используются нативные типы PostgreSQL:

- поиск «кому принадлежит 10.20.5.17» — прямой индексный поиск по `inet`;
- поиск «все адреса в 10.20.0.0/16» — оператор `<<=` по GiST-индексу;
- расчёт занятости подсети — `count` + `broadcast/network/hostmask` без прикладного кода;
- поиск по MAC (`macaddr`) с нормализацией формата.

Отчёты, которые получаются бесплатно: свободные адреса подсети, конфликты адресов, подсети без описания, VLAN без подсети, адреса без DNS-имени, устройства с management IP вне management-подсети.

## 7. Связь с логическим слоем

Логические объекты не дублируют сетевые. Приложение не хранит IP — оно ссылается на VM, у которой есть интерфейс с адресом.

```
service «1С»
  ├── DEPENDS_ON → application «1С:Предприятие 8.3»
  │                   └── RUNS_ON → vm «VM-1C-APP»
  │                                   ├── интерфейсы, IP, VLAN
  │                                   └── RUNS_ON → device «HV-02»
  │                                                   ├── rack_mount → rack «R1» U21-U22
  │                                                   ├── interface[] → connection[] → SW-CORE-01
  │                                                   └── psu[] → power_link[] → PDU R1-A / R1-B
  ├── DEPENDS_ON → database_instance «MSSQL-1C»
  ├── DEPENDS_ON → service «Active Directory»
  └── DEPENDS_ON → service «Резервное копирование»
```

Из этой структуры система отвечает на вопросы без дополнительных данных:

| Вопрос | Как считается |
|---|---|
| Что упадёт, если выключить `HV-02`? | Обход входящих `RUNS_ON` → VM → приложения → сервисы; сортировка по критичности |
| Что упадёт, если обесточить PDU R1-A? | Обход вниз по `power_link`, затем вверх по логическим зависимостям; учёт наличия стороны B |
| Какие сервисы затронет работа в стойке R1? | `rack_mount` → устройства → логические зависимости |
| Где физически находится сервис «1С»? | Вниз по зависимостям до `device` → `rack_mount` → `location.path` |
| Какие документы относятся к сервису? | `document_link` по сервису и по всем объектам его дерева зависимостей |

## 8. Влияние и критичность

Для планирования работ важно не «список объектов», а **оценка влияния**. Доменный сервис `impact_analysis(ci_id, mode)` возвращает:

- список затронутых сервисов с их критичностью и SLA;
- признак наличия резерва (второй путь питания, второй линк, кластер с HA);
- оценку простоя: `NONE` (есть резерв), `DEGRADED` (частично), `OUTAGE`;
- рекомендуемое окно работ (по пересечению `service_hours` затронутых сервисов);
- список ответственных, которых нужно уведомить.

Правила прозрачны и описаны в коде домена (`impact_rules.py`), результат включает объяснение: «простой NONE, т.к. VM работает в кластере HV-CLUSTER с двумя оставшимися узлами; питание по стороне B сохраняется».

## 9. Состояния объектов и инвентарь

Статусы CI покрывают жизненный цикл от закупки до списания: `PLANNED → ORDERED → IN_STOCK → ACTIVE → MAINTENANCE/DEGRADED → DECOMMISSIONING → RETIRED`.

Это делает систему пригодной для инвентаризации: склад — это объекты в `IN_STOCK` без `rack_mount`; планируемое оборудование (`PLANNED`) участвует в расчётах TARGET STATE, но не в текущих нагрузках.

---

## 10. Поиск по инфраструктуре

Требование «искать по IP, hostname, MAC, серийникам, портам» реализуется двумя механизмами:

1. **Точный технический поиск** — по типизированным колонкам: `inet`, `macaddr`, `lower(serial_number)`, имя интерфейса. Быстро и без ложных срабатываний.
2. **Полнотекстовый поиск** — `search_index` с полями `title`/`subtitle`/`body`/`keywords`, где `keywords` собирается из связанных записей объекта (все его IP, MAC, имена портов, серийник, инвентарный номер, hostname).

Запрос вида `10.20.5.` или `E4:5F:01` обрабатывается как префиксный/trigram-поиск, запрос `коммутатор ядра` — как полнотекстовый. Результат всегда показывает объект **и его связи** (стойка, локация, сервисы) — это требование §23.

## 11. Типовые инженерные запросы, которые обязана поддерживать модель

| Запрос | Реализация |
|---|---|
| Свободные U в каждой стойке | Агрегат по `rack_mount.u_range` против `rack.u_height` |
| Свободные порты по коммутаторам | `interface LEFT JOIN connection` |
| Где заканчивается кабель из розетки 2-14 | Трассировка `link_path` |
| Все устройства без владельца | Индекс `ix_ci_no_owner` |
| Устройства с истекающей гарантией | `device.warranty_until < now() + interval '90 days'` |
| Сертификаты, истекающие в течение 30 дней | `certificate.valid_to` |
| Объекты без документации | `ci LEFT JOIN document_link` |
| Стойки с перегрузкой по мощности | `power_node_computed.utilisation > 80` по PDU стойки |
| Сервисы без резервного копирования | Отсутствие `BACKED_UP_BY` |
| Устройства, не изменявшиеся дольше года | `audit_log` по сущности |

Каждый из этих запросов становится сохранённым фильтром (`saved_filter`) или системным отчётом (`report_definition`) — без написания нового кода.

## 12. Правила заполнения (чтобы модель не выродилась)

Модель ценна только при дисциплине ввода. Система поддерживает её техническими средствами:

1. **Обязательные поля по типу объекта** — настраиваются в реестре `custom_field` (например, для `DEVICE` обязателен серийный номер).
2. **Проверки качества данных** — фоновая задача формирует список нарушений: объект без владельца, устройство без размещения, порт с кабелем, но без описания, IP вне подсети, сервис без SLA.
3. **Дашборд качества модели** — доля объектов с заполненными владельцем, документацией и размещением. Это метрика, а не формальность: неполная CMDB бесполезна при аварии.
4. **Массовый ввод** — импорт CSV для типовых объектов (устройства, порты, адреса) с предпросмотром и валидацией до применения.
