# 06 — Diagram Engine (редактор схем)

## 1. Главное требование

Схема — не картинка, а **проекция модели**. Узел схемы ссылается на CI, линия — на реальный `connection`, `power_link` или `ci_relation`. Если изменить категорию кабеля или переименовать коммутатор, схема покажет это без перерисовки.

Из этого следует архитектурное разделение:

| Хранится в схеме | Берётся из модели при отрисовке |
|---|---|
| Какие объекты показаны | Имя, тип, статус, критичность |
| Координаты, размеры, повороты | Порты и их состояние |
| Группы, аннотации, стиль | Свойства кабеля: тип, категория, скорость, длина, маркировка |
| Изломы линий (waypoints) | Состояние связи: активна / планируется / авария |
| Viewport (зум, позиция) | Владелец, локация, связанные документы |

Таблицы: `diagram`, `diagram_node`, `diagram_edge` (см. `04-database-model.md`, §18).

---

## 2. Типы схем

| Тип | Что показывает | Источник рёбер |
|---|---|---|
| `NETWORK` | Физическая топология сети | `connection` |
| `LOGICAL` | Зависимости сервисов и систем | `ci_relation` |
| `POWER` | Однолинейная схема электропитания | `power_link` |
| `FLOORPLAN` | План помещения со стойками и трассами | `floorplan_item` (общий движок, другой рендер) |

Все четыре используют одно ядро редактора: различаются набором узлов, правилами соединения и палитрой.

---

## 3. Технологическое решение

**React Flow (xyflow)** — библиотека графового редактора.

Обоснование выбора:

| Критерий | React Flow | Свой движок на SVG | mxGraph/draw.io embed | Коммерческие (GoJS, yFiles) |
|---|---|---|---|---|
| Лицензия | MIT | — | Apache 2.0, но тяжёлый | Платные |
| Полный контроль над данными узла/ребра | да | да | ограниченно (свой формат XML) | да |
| Кастомные React-компоненты в узлах | да | нужно писать | нет | частично |
| Панорамирование, зум, выделение, миникарта | из коробки | писать самому | да | да |
| Работа в закрытом контуре | да | да | да | лицензионный сервер |
| Трудозатраты | низкие | высокие | средние | средние |

Ключевой аргумент: узел схемы должен быть полноценным React-компонентом (показывать статус, порты, нагрузку, значок критичности, контекстное меню). В React Flow это нативно, в mxGraph — через чужой формат.

Что пишем сами поверх библиотеки:
- доменные типы узлов (устройство, стойка, группа, облако, аннотация, узел питания);
- доменные типы рёбер с отображением свойств кабеля;
- привязка к реальным сущностям и синхронизация;
- автораскладка;
- undo/redo как командный стек (не «снимки состояния»);
- экспорт.

## 4. Модель редактирования

### 4.1 Команды и undo/redo

Каждое действие пользователя — команда с методами `apply` / `revert`:

```
AddNodeCommand(ci_id, position)
MoveNodesCommand([{node_id, from, to}])
ConnectCommand(source_interface_id, target_interface_id, connection_draft)
DeleteEdgeCommand(edge_id, mode: 'diagram_only' | 'delete_connection')
GroupCommand(node_ids, group_label)
StyleCommand(target_ids, style_patch)
AutoLayoutCommand(previous_positions, next_positions)
```

Стек команд лежит в Zustand-хранилище редактора. Отдельно хранится «грязное» состояние: до сохранения изменения раскладки не уходят на сервер (кроме операций, меняющих модель, — см. ниже).

### 4.2 Два класса операций

Принципиальное различие, которое видит пользователь:

| Класс | Примеры | Эффект |
|---|---|---|
| **Операции раскладки** | переместить, сгруппировать, скрыть, изменить цвет, добавить подпись | Меняют только `diagram_*`. Сохраняются по кнопке или автосохранением |
| **Операции модели** | соединить два порта, удалить кабель, изменить свойства линии, добавить устройство в систему | Меняют доменные таблицы, пишут аудит, требуют подтверждения |

Когда пользователь протягивает линию между портами, открывается компактная панель: тип, категория, длина, маркировка, статус (`PLANNED` или `ACTIVE`). После подтверждения создаётся `connection` — и ребро схемы ссылается на него.

Удаление линии всегда спрашивает: «убрать со схемы» или «удалить кабель из модели». Это защищает от потери данных при редактировании картинки.

### 4.3 Соединение по портам, а не по устройствам

Хендлы (точки соединения) узла — это его интерфейсы. Узел устройства в развёрнутом виде показывает список портов; в свёрнутом — агрегированные хендлы по сторонам. Правила:

- нельзя соединить порт, у которого уже есть активный кабель (подсветка недоступных хендлов);
- при попытке соединить несовместимые типы (RJ45 ↔ LC) выводится предупреждение с возможностью продолжить, если выбран медиаконвертер;
- линия между устройствами без указания портов допускается только на схемах типа `LOGICAL` (там ребро ссылается на `ci_relation`).

## 5. Визуализация

### 5.1 Узлы

Узел показывает: иконку роли, имя, ключевые атрибуты (модель, mgmt IP), индикатор статуса (цвет), значок критичности, счётчик проблем (открытые инциденты/задачи), индикатор занятости портов. Двойной клик — открыть карточку объекта; это выполняет требование «открывать карточку объекта прямо из схемы».

Уровни детализации по зуму:
- `< 40%` — только цветной прямоугольник и имя;
- `40–90%` — имя, роль, статус;
- `> 90%` — полный узел с портами.

Это же обеспечивает производительность на больших схемах.

### 5.2 Рёбра

Ребро кодирует свойства связи визуально:

| Свойство | Отображение |
|---|---|
| Среда (медь/оптика) | Цвет линии (медь — серый, оптика — жёлтый/оранжевый, DAC — синий) |
| Скорость | Толщина линии (1G → 1px, 10G → 2px, 40G+ → 3px) |
| Статус | Стиль: сплошная (ACTIVE), пунктир (PLANNED), красная (FAULTY), полупрозрачная (DECOMMISSIONED) |
| Резервирование | Двойная линия / метка группы |
| Маркировка, длина | Подпись на линии (включается тумблером) |
| Загрузка (в будущем, из мониторинга) | Градиент/анимация |

Параллельные линии между одной парой устройств (LAG, несколько линков) раскладываются со смещением, чтобы каждая была кликабельна.

### 5.3 Группы и аннотации

Группа (`node_kind='GROUP'`) — контейнер: «Ядро сети», «DMZ», «Серверная 205». Группы сворачиваются: содержимое скрывается, внешние связи агрегируются в одно ребро с счётчиком. Аннотации — текстовые блоки, облака (интернет/провайдер), зоны безопасности.

## 6. Автонаполнение схемы

Ручное добавление 200 устройств неприемлемо. Поддерживаются режимы наполнения:

1. **По области:** «все устройства в Серверной 205» — фильтр сохраняется в `diagram.scope`, новые объекты в этой области предлагаются к добавлению.
2. **По связям:** «SW-CORE-01 + всё, что с ним соединено, глубина 2» — обход графа `connection`.
3. **По сервису:** «всё, от чего зависит сервис 1С» — обход `ci_relation`.
4. **По стойке / по VLAN / по проекту.**

При наличии `scope` система показывает баннер «в области появилось 3 новых объекта — добавить на схему?». Схема не обязана быть полной, но не должна молча устаревать.

## 7. Автораскладка

Алгоритмы (выполняются на клиенте, детерминированно):

| Раскладка | Применение | Алгоритм |
|---|---|---|
| Иерархическая | Топология сети: ядро → распределение → доступ | Сугияма (слои по роли устройства) |
| Древовидная | Однолинейная схема питания | Layered tree сверху вниз |
| Силовая | Логические зависимости сервисов | force-directed с фиксацией выбранных узлов |
| Сетка | Стойки, патч-панели | выравнивание по сетке |

Дополнительно — точечные инструменты: выровнять по левому краю/центру, распределить равномерно, привязка к сетке (snap 8 px), фиксация узла (`pinned`), чтобы автораскладка его не двигала.

Результат автораскладки — одна команда в undo-стеке: неудачную раскладку можно отменить целиком.

## 8. Производительность

| Механизм | Эффект |
|---|---|
| Виртуализация рендера (только видимая область + запас) | 500+ узлов без падения FPS |
| Упрощение узлов при малом зуме | Меньше DOM-узлов |
| Агрегация параллельных рёбер при zoom-out | Меньше геометрии |
| Мемоизация узлов по `(ci_id, updated_at)` | Отсутствие лишних перерисовок |
| Загрузка данных схемы одним запросом (`/diagrams/{id}/full`) | Один round-trip вместо N |
| Дебаунс автосохранения раскладки (1.5 с) | Меньше записи |

Целевой порог: 500 узлов / 800 рёбер — интерактивная работа; свыше — предложение разбить схему или включить агрегацию групп.

## 9. Экспорт

| Формат | Способ | Назначение |
|---|---|---|
| **SVG** | Сериализация текущего рендера на клиенте | Векторная схема для документации |
| **PNG** | Растеризация SVG в canvas | Вставка в письма, отчёты |
| **PDF** | Серверная отрисовка SVG (WeasyPrint/ReportLab) с рамкой, штампом, датой и версией | Пакет документов для согласования |
| **JSON** | Узлы + рёбра + ссылки на CI | Резервная копия, перенос между стендами |

Экспорт в PDF/PNG помещается в MinIO и может быть **автоматически приложен к документу** (`document_version.file_id`) — это связывает схему с базой знаний: у схемы появляется версия, автор и дата пересмотра.

Импорт из Visio/draw.io в первой версии не поддерживается: сопоставление чужих фигур с реальными CI не автоматизируется без ручной разметки.

## 10. Схема и проекты (CURRENT → TARGET)

Схема умеет работать в режиме сравнения состояний:

- **Текущее состояние** — только `ACTIVE`-объекты и связи;
- **Целевое состояние** — модель с применёнными `change_item` проекта (виртуально, без записи в БД);
- **Diff-режим** — на одной схеме: существующее (серое), добавляемое (зелёный пунктир), удаляемое (красное перечёркнутое), изменяемое (жёлтая обводка).

Это даёт «схему после модернизации» без ручного рисования второй схемы и гарантирует, что целевая схема соответствует плану работ.

---

## 11. Сохранение и совместная работа

- Сохранение раскладки — `PATCH /diagrams/{id}/layout` c массивом изменённых узлов (не всей схемы).
- Оптимистическая блокировка по `diagram.version`; при конфликте предлагается перезагрузить.
- Совместное редактирование в реальном времени не реализуется (пользователь один). Архитектурно не заблокировано: команды редактора сериализуемы и могут транслироваться через WebSocket.
