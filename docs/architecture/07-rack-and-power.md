# 07 — Rack Editor и Power Model

Два тесно связанных модуля: физическое размещение в стойках и электрическая модель с расчётами. Связаны потому, что оборудование в стойке — это и юниты, и килограммы, и киловатты.

---

# Часть I. Rack Editor

## 1. Модель стойки

| Параметр | Поле | Использование |
|---|---|---|
| Высота в юнитах | `rack.u_height` (обычно 42, 47, 24) | Сетка редактора, проверка границ |
| Ширина | `width_in` (19", 10", 23") | Совместимость оборудования |
| Глубина | `depth_mm` | Проверка размещения глубокого оборудования |
| Предельный вес | `max_weight_kg` | Индикатор загрузки по весу |
| Предельная мощность | `max_power_w` | Индикатор загрузки по питанию |
| Нумерация | `descending_units` | Часть стоек нумеруется сверху вниз |
| Форм-фактор | `form_factor` | Шкаф / открытая рама / настенный |
| Координаты на плане | `plan_x`, `plan_y`, `plan_rotation` | План помещения |

Размещение: `rack_mount(rack_id, ci_id, position_u, u_height, face, depth_mm, weight_kg, is_reservation)`.

`face`: `FRONT` (фронтальная установка), `REAR` (тыловая), `FULL` (сквозная, занимает оба фасада — типично для серверов).

## 2. Правила размещения (проверяются до сохранения и в БД)

| № | Правило | Уровень проверки |
|---|---|---|
| 1 | Диапазон `[position_u, position_u + u_height)` не пересекается с занятыми на том же фасаде | `EXCLUDE USING gist` в PostgreSQL |
| 2 | `FULL` конфликтует и с `FRONT`, и с `REAR` | Два `EXCLUDE`-ограничения по генерируемым флагам `occupies_front` / `occupies_rear` |
| 3 | `position_u ≥ 1` и `position_u + u_height - 1 ≤ rack.u_height` | Триггер + доменная проверка |
| 4 | Один объект размещён не более чем в одной стойке | `UNIQUE (ci_id)` |
| 5 | Ширина устройства соответствует ширине стойки | Доменная проверка (предупреждение) |
| 6 | Глубина устройства ≤ глубины стойки | Предупреждение с подтверждением |
| 7 | Суммарный вес ≤ `max_weight_kg` | Предупреждение + индикатор |
| 8 | Суммарная мощность ≤ `max_power_w` | Предупреждение + индикатор |
| 9 | Zero-U оборудование (вертикальные PDU) не занимает юниты | `u_height = 0`, отдельная зона рендера |
| 10 | Резервирование (`is_reservation`) может конфликтовать с текущим размещением | Не блокируется; показывается как конфликт плана |

Почему часть правил — ограничения БД, а не только код: перетаскивание генерирует частые записи, а проверка «прочитал → проверил → записал» без блокировки допускает гонку. `EXCLUDE`-ограничение делает пересечение физически невозможным.

## 3. Взаимодействие

Рендер — SVG/DOM-сетка: стойка как вертикальная шкала юнитов, оборудование — блоки высотой `u_height`. Переключение фасада (FRONT/REAR) — вкладками; тыловой вид показывает PSU, порты и подключения питания.

Drag & drop на базе **dnd-kit**:

- сетка притягивает блок к границам юнита (snap = 1U);
- при перетаскивании подсвечивается целевой диапазон: зелёный — можно, красный — конфликт, жёлтый — можно с предупреждением (вес/глубина/питание);
- блокировка «сквозь» занятые юниты: элемент не «проваливается» в занятую зону;
- перетаскивание между стойками в двухпанельном режиме;
- перетаскивание из «склада» (оборудование в статусе `IN_STOCK`) прямо в стойку — это и есть ввод в эксплуатацию;
- `Alt`+drag — создать резервирование места вместо перемещения.

Клавиатура: `↑/↓` — сдвиг на 1U, `Shift+↑/↓` — на 5U, `F` — сменить фасад, `Delete` — извлечь из стойки (объект переходит в `IN_STOCK`, а не удаляется), `Enter` — карточка объекта.

## 4. Что показывает стойка

| Элемент | Данные |
|---|---|
| Блок оборудования | Имя, модель, роль (цвет), статус, владелец, мощность |
| Свободные юниты | Подсвеченные пустые полосы с подписью размера непрерывного блока («3U свободно») |
| Шкала загрузки | Занято U / всего, вес, мощность, % от лимитов |
| Вертикальные PDU | Слева/справа от сетки, с указанием стороны A/B |
| Патч-панели | С номерами портов; клик по порту → интерфейс → кабель |
| Индикаторы питания | Для каждого устройства: подключено к PDU A / B / только один ввод (предупреждение) |
| Проблемы | Значок, если у объекта открытый инцидент или просроченная задача |

Отчёты, вытекающие из модели: свободные непрерывные блоки по стойкам (можно ли поставить 4U-сервер), самые загруженные стойки, стойки без резерва питания, оборудование без стороны B.

## 5. Экспорт

Вид стойки экспортируется в SVG/PNG/PDF (elevation-схема с подписями) и включается в проектную документацию — так же, как схемы сети.

# Часть II. Power Model

## 6. Топология питания

Электрическая схема — направленный ациклический граф (DAG) узлов `power_node`, соединённых рёбрами `power_link`.

```
INPUT «Ввод №1»  20 кВт, 3ф, 400 В, 3×32А
  └─ PANEL «ЩС-1»
      ├─ BREAKER «QF1» C32, 3ф ──► LINE «Л-1» 5×6 мм² ──► UPS «APC SRT 20k»
      │                                                      ├─ PDU «R1-PDU-A» (стойка R1, сторона A)
      │                                                      │    └─ OUTLET «C13-07» ─► PSU «SRV-01 PSU1» ─► device SRV-01
      │                                                      └─ PDU «R2-PDU-A»
      └─ BREAKER «QF2» C32, 3ф ──► LINE «Л-2» ──────────────► PDU «R1-PDU-B» (сторона B, без UPS)
```

Типы узлов: `INPUT`, `PANEL`, `BREAKER`, `LINE`, `TRANSFER_SWITCH`, `UPS`, `PDU`, `OUTLET`, `PSU`, `GENERIC_LOAD`.

Каждый узел — это CI, поэтому у него есть владелец, статус, документы, задачи, изменения и история наравне с остальными объектами.

### 6.1 Мощность: четыре разные величины, которые нельзя смешивать

Это критично для проектов увеличения мощности: если хранить одно поле «мощность», расчёт даёт красивое, но бесполезное число. Поэтому у оборудования и узлов хранятся раздельно:

| Величина | Поле | Что это | Источник |
|---|---|---|---|
| **Номинальная** | `power_nameplate_w` | Типовое потребление по паспорту производителя | Каталог `device_model` или паспорт экземпляра |
| **Максимальная** | `power_max_w` | Пиковое потребление (шильдик БП, пусковые режимы) | Паспорт |
| **Расчётная** | `power_estimated_w` | Ожидаемое потребление: номинал × коэффициент использования + потери | Вычисляется, хранится в `power_node_computed` |
| **Фактическая** | последняя запись `power_measurement` | Реальное измерение | Замер клещами, показания PDU/UPS, будущая телеметрия |

Фактические значения хранятся **историей измерений**, а не одним полем:

```sql
CREATE TABLE power_measurement (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  node_id       uuid NOT NULL REFERENCES power_node(id) ON DELETE CASCADE,
  measured_at   timestamptz NOT NULL,
  power_w       integer,
  current_a     numeric(7,2),
  voltage_v     numeric(6,1),
  power_factor  numeric(4,3),
  phase_label   phase_label,          -- для пофазного замера
  source        text NOT NULL,        -- MANUAL | PDU | UPS | METER | IMPORT | MONITORING
  measured_by   uuid REFERENCES employee(id) ON DELETE SET NULL,
  instrument    text,                 -- чем измеряли
  note          text,
  is_peak       boolean NOT NULL DEFAULT false
);
CREATE INDEX ix_power_measurement_node_time ON power_measurement(node_id, measured_at DESC);
```

Правила использования в расчёте:

1. Приоритет источников для узла: **свежее измерение** (не старше `measurement_ttl_days`, по умолчанию 180) → **расчётная** → **номинальная**.
2. Источник, дата и способ получения каждого значения указываются в трассе расчёта: `«PDU R1-A: измерение 3 840 Вт от 15.09.2026, источник PDU»` или `«SRV-03: расчёт 840 Вт = 1200 × 0.70, измерений нет»`.
3. Устаревшее измерение не выбрасывается, а помечается как просроченное и попадает в отчёт «узлы без актуальных замеров».
4. Расхождение измерения и расчёта более чем на 25% формирует предупреждение: либо неверный коэффициент, либо неучтённая нагрузка.

### 6.2 Электрические параметры узла

| Параметр | Поле | Для каких узлов |
|---|---|---|
| Напряжение | `voltage_v` (230 / 400) | все |
| Число фаз | `phases` (1 или 3) | ввод, щит, автомат, линия, UPS, PDU |
| Фаза подключения | `phase_label` (L1 / L2 / L3 / L1L2L3) | однофазные потребители — обязательно |
| Номинальный ток | `rated_current_a` | автоматы, линии, PDU, вводы |
| Кривая/тип автомата | `breaker_curve` (B / C / D), `breaker_poles` (1P / 3P / 3P+N) | автоматы |
| Кабель линии | `cable_spec` (`5×6 мм², ВВГнг`), `cable_length_m`, `cable_ampacity_a` | линии |
| Допустимая длительная нагрузка | `rated_current_a × derating_factor` | автоматы, линии |
| cos φ | `power_factor` (по умолчанию 0.95 для ИТ-нагрузки с PFC) | нагрузки |
| КПД | `efficiency` | UPS (0.94–0.97), PSU (0.90–0.94) |
| Предел мощности | `max_load_w` | ограничивающие узлы |
| Ёмкость UPS | `ups_capacity_va`, `ups_capacity_w`, `ups_battery_minutes` | UPS |
| Ветка питания | `feed_id` → `power_feed` | все узлы, кроме точки схождения |

Все расчёты ведутся в токах и мощностях одновременно: ограничение автомата — это ток, ограничение UPS — мощность, ограничение ввода — и то и другое. Считать только киловатты недостаточно: однофазная нагрузка 5 кВт на L1 при трёхфазном вводе 3×32 А означает 21.7 А на одной фазе, и именно это определяет перегрузку.

### 6.3 Баланс фаз

Для каждого трёхфазного узла считается:

```
load_L1, load_L2, load_L3   (Вт и А)
disbalance = (max(L) − min(L)) / avg(L) × 100%
```

Норматив по умолчанию — не более 15% (настраивается). Превышение даёт предупреждение с конкретным предложением: какие однофазные потребители перенести на другую фазу и какой эффект это даст. При добавлении однофазного потребителя в сценарии система сама предлагает наименее загруженную фазу.

### 6.4 Инварианты

1. Граф без циклов (проверка рекурсивным CTE при создании `power_link`).
2. Узел может иметь несколько родителей только при вводе резерва (`TRANSFER_SWITCH`) или у оборудования с несколькими PSU — пути A и B независимы.
3. Однофазный потребитель обязан иметь `phase_label`, иначе объект помечается как дефект данных и исключается из расчёта баланса.
4. Узел принадлежит ровно одной ветке (`feed_id`); оборудование с двумя PSU принадлежит двум веткам через свои PSU.
5. Сумма номиналов автоматов группы не обязана укладываться в номинал вышестоящего — это нормальная практика, проверяется расчётная нагрузка, а не сумма номиналов.

## 6a. A/B питание как самостоятельная сущность

Резервирование питания — не атрибут, а структура. Поэтому ветка питания выделена в отдельную сущность:

```sql
CREATE TABLE power_feed (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name           text NOT NULL,              -- «Луч A», «Луч B»
  side           feed_side NOT NULL,         -- A | B | SINGLE
  root_node_id   uuid NOT NULL REFERENCES power_node(id) ON DELETE RESTRICT,  -- ввод
  location_id    uuid REFERENCES location(id) ON DELETE SET NULL,
  is_protected   boolean NOT NULL DEFAULT false,   -- есть ли UPS/ДГУ на ветке
  description    text,
  UNIQUE (location_id, name)
);
ALTER TABLE power_node ADD COLUMN feed_id uuid REFERENCES power_feed(id) ON DELETE SET NULL;
```

Типовая картина:

```
Server-01
 ├── PSU-A → Outlet A7 → PDU-A → UPS-A → QF1 → Ввод A     (power_feed «Луч A»)
 └── PSU-B → Outlet B4 → PDU-B → UPS-B → QF2 → Ввод B     (power_feed «Луч B»)
```

### 6a.1 Анализ отказоустойчивости

Отдельный доменный сервис `failover_analysis(feed_id)` отвечает на вопрос **«при отказе ветки A оборудование продолжит работу?»**. Для каждого потребителя:

| Вердикт | Условие |
|---|---|
| `RESILIENT` | Есть питание минимум от двух разных веток, и оставшаяся ветка выдерживает полную нагрузку потребителя |
| `AT_RISK` | Два ввода есть, но оставшаяся ветка перегружается (расчётная нагрузка > допустимой) |
| `SINGLE_FEED` | Питание только от одной ветки — при отказе оборудование обесточится |
| `SAME_FEED` | Формально два PSU, но оба сидят на одной ветке (частая реальная ошибка монтажа) |
| `UNKNOWN` | Цепочка питания не заполнена до конца |

Алгоритм:

```
для каждой ветки F:
    отключить F (виртуально)
    для каждого потребителя C:
        пути = все цепочки питания C, не проходящие через F
        если путей нет            → SINGLE_FEED (или SAME_FEED, если все PSU были в F)
        иначе:
            пересчитать нагрузку оставшихся веток с учётом переноса нагрузки C
            если любой узел пути превышает допустимую нагрузку → AT_RISK
            иначе → RESILIENT
    агрегировать: список пострадавших сервисов через логические зависимости
```

Результат используется в трёх местах: дашборд (блок «нарушения резервирования»), карточка объекта (бейдж «нет резерва по питанию»), планирование работ (перед отключением луча система показывает, что именно погаснет). Проверка запускается при изменении электрической модели и по расписанию.

Важное следствие: при переносе нагрузки на одну ветку UPS и PDU этой ветки должны выдержать **двойную** нагрузку — именно это и проверяется, а не «есть два кабеля, значит всё хорошо».

## 7. Методика расчёта

Расчёт выполняется чистой функцией над выгруженным в память графом (`domain/power/calculator.py`). Величины считаются раздельно и никогда не смешиваются:

| Величина | Что это | Откуда |
|---|---|---|
| **Nameplate (номинальная)** | Сумма паспортных типовых мощностей | `power_nameplate_w` экземпляра или модели |
| **Peak (максимальная)** | Сумма пиковых значений — для проверки автоматов и пусковых режимов | `power_max_w` |
| **Estimated (расчётная)** | Ожидаемое потребление: номинал × коэффициент использования + потери | Вычисляется |
| **Measured (фактическая)** | Последнее актуальное измерение с датой и источником | `power_measurement` |

Каждое значение в результате сопровождается признаком происхождения (`source`: `MEASUREMENT` / `ESTIMATE` / `NAMEPLATE`) и, для измерений, датой и способом получения. Смешивание источников внутри одной суммы допускается (часть узлов измерена, часть — нет), но доля измеренных данных выводится явно: «расчёт основан на 62% измеренных значений».

Коэффициенты использования по умолчанию (настраиваются в справочнике):

| Класс оборудования | Коэффициент |
|---|---|
| Серверы | 0.70 |
| СХД | 0.75 |
| Сетевое оборудование | 0.85 |
| Оборудование с PoE | 0.85 + фактическая PoE-нагрузка |
| Прочее | 0.80 |

### 7.1 Алгоритм

```
1. Загрузить узлы, рёбра и ветки питания (по площадке/помещению или целиком).
2. Проверить ацикличность, построить топологический порядок.
3. Для листьев (PSU / GENERIC_LOAD) вычислить базовое потребление
   по приоритету источников: актуальное измерение → расчёт → номинал:
     nameplate = power_nameplate_w
     estimated = power_nameplate_w × utilization_factor
     если есть измерение не старше TTL — используется оно
   Если у устройства N блоков питания с резервированием (N+1),
   нагрузка делится между активными путями A/B, а не умножается.
4. Снизу вверх: нагрузка узла = Σ нагрузок потомков.
5. На UPS и PSU добавить потери: P_in = P_out / efficiency.
6. На UPS при режиме заряда добавить резерв на подзаряд батарей
   (по умолчанию 10% от номинала, настраивается).
7. Для трёхфазных узлов распределить нагрузку по фазам:
     трёхфазные потребители — поровну на L1/L2/L3;
     однофазные — на свою phase_label.
8. Рассчитать токи:
     однофазный:  I = P / (U × cosφ)
     трёхфазный:  I = P / (√3 × U_линейное × cosφ)
9. Сравнить с пределами:
     для автомата: допустимо  I ≤ rated_current_a × derating_factor (0.8)
     для UPS:      допустимо  P ≤ ups_capacity_va × 0.9 (типовой power factor)
     для ввода:    допустимо  P ≤ max_load_w
10. Рассчитать баланс фаз и дисбаланс для трёхфазных узлов.
11. Выполнить анализ отказоустойчивости по веткам (см. §6a.1):
    для каждой ветки — виртуальное отключение и перенос нагрузки на оставшиеся.
12. Записать результат, источники значений и трассу расчёта в power_node_computed.
```

### 7.2 Прозрачность расчёта

  "limit_w": 8000,
  "headroom_w": 3870,
  "current_a": { "L1": 6.3, "L2": 5.9, "L3": 6.1 },
  "value_source": "MIXED",
  "measured_coverage_pct": 62,
  "calculation_trace": [
    { "step": 1, "source": "SRV-1C-01 / PSU1", "value_source": "MEASUREMENT",

### 7.3 Что считается на каждом уровне

| Уровень | Показатели |
|---|---|
| Ввод | Суммарная нагрузка, ток по фазам, дисбаланс фаз, резерв до номинала |
| Щит | Нагрузка по группам, свободные места под автоматы |
| Автомат | Ток, % от номинала с учётом derating, признак перегрузки |
| Линия | Ток, сечение/допустимый ток (справочник), падение напряжения (опционально) |
| UPS | Нагрузка в Вт и ВА, % загрузки, расчётное время автономии, запас на подзаряд |
| PDU | Нагрузка, % от номинала, ток по фазам, свободные розетки |
| Стойка | Суммарная нагрузка по обеим сторонам, % от `rack.max_power_w` |
| Помещение | Суммарная нагрузка, резерв ввода, тепловыделение (кВт → кВт холода) |

Тепловыделение считается как `Q ≈ P` (практически вся электрическая мощность ИТ-оборудования переходит в тепло) и сопоставляется с мощностью кондиционирования, если она внесена в модель.

## 8. Сценарное моделирование («что если»)

### 8.1 Механика

```
power_scenario (привязан к проекту)
  ├─ base_snapshot_id  → зафиксированное текущее состояние
  └─ power_scenario_item[]
        ADD     + 2 × сервер модели R650 (2 PSU, 1200 Вт), в стойку R2, сторона A/B
        ADD     + 1 × СХД модели ME5024 (1600 Вт)
        ADD     + 2 × коммутатор 350 Вт
        ADD     + 1 × UPS 10 кВА (КПД 0.94)
        MODIFY    ввод: 20 кВт → 30 кВт (планируемое увеличение)
```

Расчёт сценария использует тот же калькулятор: строится копия графа в памяти, к ней применяются элементы сценария, вызывается тот же алгоритм. Никакой отдельной «сценарной математики» нет — иначе прогноз и факт разошлись бы.

### 8.2 Пример из задания

Исходное состояние серверной:

| Показатель | Значение |
|---|---|
| Ввод | 20 кВт (3×32 А, 400 В, cos φ 0.95) |
| Connected (сумма шильдиков) | 24.0 кВт |
| Estimated (расчётная) | 16.8 кВт |
| Measured (по счётчику UPS) | 13.4 кВт |
| Резерв к расчётной | 20.0 − 16.8 = **3.2 кВт (16%)** |

Планируемое добавление:

| Оборудование | Кол-во | Шильдик | Коэф. | Расчётная |
|---|---|---|---|---|
| Сервер R650 | 2 | 1200 Вт | 0.70 | 1680 Вт |
| СХД ME5024 | 1 | 1600 Вт | 0.75 | 1200 Вт |
| Коммутатор | 2 | 350 Вт | 0.85 | 595 Вт |
| **Итого нагрузка** | | **4700 Вт** | | **3475 Вт** |
| Потери нового UPS (КПД 0.94) | | | | +222 Вт |
| **Итого прирост** | | | | **3697 Вт** |

Прогноз:

| Показатель | Текущее | Целевое | Комментарий |
|---|---|---|---|
| Estimated | 16.80 кВт | **20.50 кВт** | 16.8 + 3.70 |
| Резерв к вводу 20 кВт | +3.20 кВт | **−0.50 кВт** | **дефицит** |
| Пик при подзаряде батарей (+0.9 кВт) | — | **21.40 кВт** | дефицит 1.40 кВт |
| Требуемый ввод при политике запаса 20% | 21.0 кВт | **25.6 кВт** | 20.5 / 0.8 |
| Рекомендация | — | **3×50 А (≈32.9 кВт)** | √3 × 400 × 50 × 0.95 |

Вывод системы: **дефицит мощности 0.5 кВт по расчётной нагрузке и 5.6 кВт с учётом нормативного запаса. Требуется увеличение ввода до 3×50 А.**

Дополнительно проверяется баланс фаз:

| Фаза | Текущая | После | Дисбаланс |
|---|---|---|---|
| L1 | 5.9 кВт | 7.2 кВт | |
| L2 | 5.4 кВт | 6.8 кВт | |
| L3 | 5.5 кВт | 6.5 кВт | 10.8% (норма ≤ 15%) |

И резервирование: новые серверы подключаются двумя PSU (A и B); при отказе стороны A сторона B принимает 100% нагрузки двухвводных потребителей — проверяется, что PDU и UPS стороны B это выдерживают.

### 8.3 Результат сценария

Сценарий порождает:
1. **Отчёт по мощности** (PDF/XLSX) — текущее, целевое, дефицит, обоснование расчёта. Это основа пакета документов для согласования с управляющей компанией.
2. **Список необходимых изменений** — новые автоматы, линии, UPS, PDU, увеличение ввода.
3. **`planned_change` + `change_item[]`** — целевое состояние инфраструктуры, готовое к применению после реализации проекта.
4. **Задачи проекта** — по шаблону работ (см. `08-project-management.md`).

Ни одно из этих действий не изменяет текущую модель: до реализации проект живёт в отдельном слое.

## 9. Связь питания с остальной системой

| Связь | Значение |
|---|---|
| `power_node.parent_device_id` | PSU принадлежит устройству → в карточке сервера видно всю цепочку до ввода |
| `power_node.rack_id` | Нагрузка агрегируется по стойкам |
| `power_link` → диаграммы | Однолинейная схема строится автоматически из DAG |
| `change_ci` | Работы с электрикой фиксируются как изменения с указанием затронутых узлов |
| `impact_analysis` | «Что обесточится при отключении QF1» — обход вниз по DAG и далее по логическим зависимостям |
| `maintenance_window` | Плановое отключение фиксируется окном с перечнем затрагиваемых сервисов |

## 10. Ограничения первой версии

Сознательно не реализуется:

- расчёт токов короткого замыкания, селективности защит и падения напряжения по длине линии (требует справочников кабельной продукции и выходит за рамки управления ИТ-хозяйством);
- гармоники и реактивная мощность сверх учёта cos φ;
- автоматический сбор телеметрии с PDU/UPS (это Integration Layer, Phase 8+);
- тепловое моделирование помещения (учитывается только суммарное тепловыделение).

Каждое из этих ограничений может быть снято без изменения схемы данных: добавляются поля справочников и новые шаги в калькулятор.
