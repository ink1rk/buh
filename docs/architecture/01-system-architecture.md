# 01 — Системная архитектура ITMS

> **Статус документа:** проект архитектуры, ожидает согласования.
> Код системы не пишется до утверждения этого и связанных документов.

## 1. Что мы строим

**ITMS (IT Management System)** — self-hosted система для управления ИТ-инфраструктурой, ИТ-отделом, проектами, эксплуатацией и документацией.

Система строится вокруг одной идеи:

> В системе нет независимых разделов. Есть **единый граф объектов ИТ-ландшафта** и разные проекции этого графа: таблицы, карточки, схемы, стойки, электрическая модель, проекты, отчёты.

Раздел «Серверы» — это не отдельная база, а фильтр по графу. Схема сети — не картинка, а визуальная проекция тех же узлов и рёбер. Проект — не список задач, а описание перехода графа из состояния CURRENT в состояние TARGET.

### 1.1 Что система не является

| Не является | Почему это важно |
|---|---|
| Wiki | Документ всегда привязан к объектам инфраструктуры, имеет версии, владельца и дату пересмотра |
| Таск-менеджером | Задача привязана к CI, изменению, проекту, сервису; задача — часть модели, а не самоцель |
| HelpDesk-порталом | Нет публичного приёма обращений, нет очередей внешних пользователей |
| Multi-tenant SaaS | Один владелец, один контур, один экземпляр |
| CRUD-набором страниц | Ценность — связи, расчёты и переходы состояний, а не формы ввода |

### 1.2 Модель пользователей

Система однопользовательская по управлению и многопользовательская по данным:

- **Owner (руководитель ИТ)** — единственная учётная запись с полным доступом. Все операции записи по умолчанию выполняет он.
- **Employee (сотрудник ИТ-отдела)** — сущность справочника: исполнитель задач, ответственный за объект, участник проекта. **Не обязан иметь учётную запись.**
- **Executor account** (Phase 6, опционально) — ограниченный вход исполнителя: свои задачи, свои плановые работы, чтение документации. Архитектурно заложен (таблицы `app_user`, `role`, `permission`), но в Phase 1–5 не включается.

Разделение `employee` (человек в оргструктуре) и `app_user` (учётная запись) — принципиальное. Оно позволяет вести полноценный ИТ-отдел с загрузкой и зонами ответственности, не заводя логины и не превращая систему в корпоративную платформу.

## 3. Текущее состояние репозитория и способ размещения ITMS

Репозиторий сейчас содержит **другой продукт** — «Personal Finance AI»:

| Компонент | Стек | Отношение к ITMS |
|---|---|---|
| `backend/` | FastAPI, SQLAlchemy 2.0 async, SQLite, Alembic, Pydantic v2 | Стек совпадает с рекомендуемым, код переиспользовать нельзя (другая предметная область) |
| `frontend/` | React 19, TypeScript, Vite, Tailwind v4, TanStack Query, Zustand, React Router | Стек совпадает, дизайн-система не подходит (glassmorphism-финансовый UI) |
| `deploy/`, `docker-compose*.yml` | Docker, nginx, Ubuntu installer | Шаблон деплоя переиспользуем |

**Решение:** ITMS размещается как отдельное приложение в том же репозитории, не затрагивая существующий код:

```
/itms
  /api          FastAPI-приложение ITMS (независимый deployable)
  /web          React SPA ITMS (независимый bundle)
  /worker       фоновые задачи (переиспользует пакет api как библиотеку)
  /deploy       docker-compose, nginx, backup-скрипты ITMS
/docs           архитектура (этот пакет документов)
/backend        существующее финансовое приложение — без изменений
/frontend       существующее финансовое приложение — без изменений
```

Обоснование: продукты не разделяют ни одной доменной таблицы и имеют разный жизненный цикл. Смешивание в общий `backend/app` дало бы связанность без выгоды, общий образ и общую БД без причины. Отдельное дерево даёт независимый деплой, независимые миграции и возможность вынести ITMS в свой репозиторий одним `git subtree split`.

Альтернативы, которые были отклонены:

| Вариант | Почему отклонён |
|---|---|
| Пакет `backend/app/itms` внутри финансового API | Один процесс и одна БД для двух несвязанных продуктов; миграции Alembic конфликтуют; риск сломать работающее приложение |
| Полная замена содержимого репозитория | Нарушает требование не ломать существующую функциональность |
| Микросервисы по модулям ITMS | Домен сильно связный (граф), распределённые транзакции и распределённые джойны без выгоды |

## 4. Стиль архитектуры

**Модульный монолит с чётко очерченными доменными модулями, ports & adapters на границах.**

Почему монолит: центральная ценность продукта — связность. Запрос «покажи всё, что относится к SERVER-01» затрагивает CMDB, сеть, питание, документы, задачи, изменения. В монолите это один SQL-запрос по графу; в микросервисах — оркестрация пяти сервисов ради того же результата. Нагрузка — один пользователь и десятки тысяч объектов, горизонтальное масштабирование не требуется.

Почему модульный: модули изолированы на уровне пакетов и правил импорта, чтобы систему можно было развивать и при необходимости разрезать.

### 4.1 Слои

```
┌──────────────────────────────────────────────────────────────┐
│ api/            HTTP-роутеры. Валидация DTO, авторизация,    │
│                 сериализация. Без бизнес-логики.             │
├──────────────────────────────────────────────────────────────┤
│ services/       Прикладные сценарии (use cases). Транзакция, │
│                 оркестрация, публикация доменных событий.    │
├──────────────────────────────────────────────────────────────┤
│ domain/         Чистая логика: расчёт нагрузок, валидация    │
│                 размещения в стойке, трассировка кабелей,    │
│                 прогресс проекта, диффы состояний.           │
│                 Без SQLAlchemy, без FastAPI, тестируется     │
│                 без базы.                                    │
├──────────────────────────────────────────────────────────────┤
│ models/         SQLAlchemy ORM, constraints, индексы.        │
├──────────────────────────────────────────────────────────────┤
│ infra/          Адаптеры: PostgreSQL, Redis, S3, экспортёры  │
│                 PDF/XLSX, будущие интеграции.                │
└──────────────────────────────────────────────────────────────┘
```

Правило импорта (проверяется линтером `import-linter`):
`api → services → domain`, `services → models → infra`. Обратные импорты запрещены. `domain` не импортирует ничего из проекта, кроме себя.

Практический смысл: расчёт электрической нагрузки, проверка размещения 2U-сервера в стойке и расчёт критического пути проекта — это чистые функции над dataclass-структурами. Они покрываются unit-тестами без БД и переиспользуются в трёх местах: API, воркер, экспорт отчётов.

## 5. Сквозные механизмы

### 5.1 Аудит и история (обязателен для всей системы)

Аудит не реализуется в каждом модуле отдельно. Он встроен в единицу работы:

1. Все ORM-классы, требующие истории, наследуют миксин `Auditable`.
2. SQLAlchemy-события `before_flush` собирают грязные объекты и вычисляют diff по полям.
3. На коммите пишется `audit_log` (кто, что, когда, откуда, комментарий) и набор `audit_change` (поле, старое значение, новое значение — в `jsonb`).
4. Контекст актора (`current_actor`, `request_id`, `source`) передаётся через `contextvars`, поэтому воркер и импортёр пишут аудит так же, как HTTP-запрос.

Детали — в `docs/domain-model/02-domain-model.md`, раздел «История изменений».

### 5.2 Доменные события и outbox

Изменения публикуют события (`ci.created`, `connection.changed`, `power.load.recalculated`, `document.review_due`). События пишутся в таблицу `outbox` в той же транзакции и разбираются воркером. Это даёт:

- пересчёт производных величин (нагрузка по стойке/PDU/UPS) вне HTTP-запроса;
- переиндексацию поиска;
- ленту активности;
- готовую точку подключения будущих интеграций (без изменения доменного кода).

### 5.3 Расчётные величины и кэш

Тяжёлые производные величины (нагрузка узлов питания, занятость стоек, прогресс проектов, здоровье сервисов) считаются доменными функциями и кэшируются в таблицах `*_computed` с полем `computed_at` и версией формулы. Любое значение можно объяснить: API отдаёт не только число, но и **трассу расчёта** — список вкладов с формулой. Требование «расчёты должны быть прозрачными» решается на уровне контракта API, а не комментариями в коде.

### 5.4 Конкурентный доступ и целостность

- Оптимистическая блокировка: у изменяемых сущностей есть `version`; `PATCH` принимает `If-Match`, конфликт → `409`.
- Инварианты физического мира (перекрытие U в стойке, два кабеля в один порт, петля в дереве локаций) обеспечиваются **ограничениями PostgreSQL**, а не только проверками в коде. Ошибка БД транслируется в понятное сообщение API.
- Массовые операции (применение TARGET STATE, импорт) — в одной транзакции с сохранением результата в `job`.

### 5.5 Ошибки и наблюдаемость

- Единый формат ошибок RFC 7807 (`application/problem+json`): `type`, `title`, `status`, `detail`, `errors[]`, `request_id`.
- Логи структурные (structlog, JSON), в каждой записи `request_id`, `actor_id`, `module`.
- `/health`, `/ready`, метрики Prometheus-формата на `/metrics` (без внешнего сервиса, скрейпить по желанию).

## 6. Технологический стек

### 6.1 Backend

| Технология | Версия | Обоснование |
|---|---|---|
| Python | 3.12 | Требование заказчика; зрелая экосистема для работы с сетями/электрикой (`ipaddress`, `networkx`) |
| FastAPI | 0.115+ | Требование заказчика; OpenAPI из коробки, DI, Pydantic-валидация |
| SQLAlchemy | 2.0 async | Требование заказчика; нужен полноценный SQL (рекурсивные CTE, оконные функции, `EXCLUDE`-ограничения), ORM-обёртки типа Tortoise этого не дают |
| Pydantic | v2 | Контракты API, валидация, сериализация |
| Alembic | 1.14+ | Миграции; обязательны с первого дня |
| PostgreSQL | 16 | Типы `inet`/`cidr`/`macaddr`/`jsonb`/`tstzrange`, `EXCLUDE USING gist`, рекурсивные CTE, FTS, `pg_trgm`. Ни одна из этих возможностей не заменяется приложением дёшево |
| Redis | 7 | Кэш, очередь задач, распределённые локи на пересчёт |
| ARQ | 0.26+ | Воркер на asyncio поверх Redis. Проще Celery, не тянет собственный протокол и брокер |
| MinIO | последняя LTS | S3-совместимое хранилище файлов; локально, без внешних сервисов |
| openpyxl / WeasyPrint | — | XLSX и PDF отчёты на сервере, без внешних API |
| pytest + testcontainers | — | Тесты на реальном PostgreSQL: половина инвариантов живёт в БД, SQLite их не проверит |

**Почему PostgreSQL-специфичные возможности — осознанный выбор:** система не должна быть переносимой на другую СУБД. Отказ от `EXCLUDE`-ограничений и `inet` ради абстрактной переносимости означал бы перенос проверок в приложение и гонки при конкурентных изменениях.

### 6.3 Инфраструктура

Docker Compose с сервисами: `itms-api`, `itms-worker`, `itms-web` (nginx со статикой и прокси), `postgres`, `redis`, `minio`, `backup` (pg_dump + mc mirror по расписанию). Kubernetes, Elasticsearch, service mesh — не используются.

## 7. Данные и хранение

| Тип данных | Где хранится | Причина |
|---|---|---|
| Доменные сущности и связи | PostgreSQL, нормализованные таблицы | Целостность, джойны, ограничения |
| Произвольные атрибуты объектов | `ci.attributes jsonb` + реестр `custom_field` | Расширяемость без миграций; типизированные поля остаются колонками |
| Схемы (диаграммы) | PostgreSQL: узлы/рёбра — ссылки на CI, раскладка — `jsonb` | Схема отражает актуальные данные, а не копию |
| Файлы, вложения, экспорты | MinIO; метаданные в `file_object` | Не раздуваем БД; версионирование и дедупликация по sha256 |
| Тексты документов | PostgreSQL (`document_version.body_md`) | Нужны версии, поиск и diff |
| Поисковый индекс | PostgreSQL `search_index` + `tsvector`/`pg_trgm` | Одна СУБД вместо отдельного поискового движка |
| Кэш, очередь, локи | Redis | Эфемерные данные |

**Резервное копирование:** `pg_dump` (логический) + `mc mirror` содержимого MinIO по расписанию; восстановление — задокументированная процедура. Файлы и БД бэкапятся согласованно (сначала БД, затем объекты — объекты иммутабельны, поэтому расхождение безопасно).

## 8. Безопасность

Контур закрытый, но базовые меры обязательны:

- Сессии в httpOnly-cookie (`SameSite=Lax`, `Secure` за TLS), серверные записи сессий с возможностью отзыва; пароль — Argon2id.
- CSRF: double-submit token на все небезопасные методы.
- Rate limiting на вход и на тяжёлые операции (экспорт, пересчёт).
- Проверки прав — только на сервере; фронт скрывает элементы, но не является границей безопасности.
- Загрузка файлов: белый список MIME, санация имени, проверка сигнатуры, хранение вне web-root в MinIO, отдача через подписанные временные URL, `Content-Disposition: attachment` для всего, кроме явно безопасных типов.
- Полная параметризация SQL (SQLAlchemy), запрет строковой сборки запросов; для конструктора отчётов — whitelist полей и операторов, а не произвольный SQL.
- Публичной регистрации нет; первая учётная запись создаётся установочной командой.

## 9. Ключевые архитектурные решения (ADR-сводка)

| № | Решение | Альтернатива | Почему так |
|---|---|---|---|
| 1 | Единая таблица `ci` + наследование по типам (joined-table inheritance) | Отдельные несвязанные таблицы на каждый тип объекта | Универсальные связи, документы, задачи, аудит и поиск работают для всех типов без дублирования |
| 2 | Топология (порты, кабели, питание, U-позиции) — отдельные типизированные таблицы, а не generic-связи | Всё в `ci_relation` | Нужны специфичные атрибуты и ограничения БД: категория кабеля, фаза, диапазон U |
| 3 | Логические связи — в `ci_relation` с типом | Таблица на каждый вид связи | Гибкость: новый тип связи не требует миграции |
| 4 | Модульный монолит | Микросервисы | Домен связный, пользователь один, распределённые джойны не нужны |
| 5 | Проект = переход CURRENT → TARGET, а не отдельный список задач | Проект как контейнер задач | Требование §21: проект обязан менять инфраструктуру и обновлять модель по завершении |
| 6 | Расчёты — чистые функции + трасса расчёта в ответе API | Расчёты в SQL/во вьюхах | Прозрачность, объяснимость, тестируемость, переиспользование в сценариях «что если» |
| 7 | PostgreSQL FTS вместо Elasticsearch | Внешний поисковый движок | Объём данных мал, требование прямо запрещает лишние сервисы |
| 8 | React Flow для схем, собственный SVG-движок для стоек/планов/Gantt | Готовые коммерческие компоненты | Линии схемы обязаны быть связаны с сущностью `connection`; в стойке нужна своя физика размещения |
| 9 | Аудит через unit-of-work, а не через триггеры БД | Триггеры PostgreSQL | Нужен контекст актора, комментарий к изменению и связь с `change`; в триггере этого контекста нет |
| 10 | Отдельное дерево `/itms` в репозитории | Встраивание в существующий `backend/` | Независимый деплой и миграции, не ломает существующий продукт |

## 10. Нефункциональные требования

| Параметр | Цель | Как достигается |
|---|---|---|
| Объём данных | до ~50 000 CI, ~200 000 интерфейсов, ~500 000 записей аудита | Индексы, пагинация, серверная фильтрация |
| Отклик списков | < 200 мс на 10 000 строк | Keyset-пагинация, покрывающие индексы, виртуализация таблиц |
| Отклик карточки объекта со связями | < 400 мс | Один рекурсивный CTE + агрегаты, без N+1 |
| Схема сети | плавно до ~500 узлов | Виртуализация рендера, упрощение рёбер при zoom-out |
| Пересчёт питания | < 1 с на 1000 узлов | Топологическая сортировка DAG в памяти |
| Доступность | перезапуск без потери данных | Все состояния в БД/MinIO; воркер идемпотентен |
| Восстановление | из бэкапа по инструкции | Документированная процедура + проверка восстановления |

## 11. Integration Layer (закладка на будущее, сейчас не реализуется)

Точки расширения, которые закладываются в модель **сейчас**, чтобы потом не переписывать ядро:

1. Поля происхождения данных у каждого CI: `source_system`, `external_id`, `is_managed_externally`, `last_synced_at`. Объект, пришедший из Zabbix/AD, помечается и защищается от затирания ручными правками (или наоборот — ручные правки фиксируются как отклонение).
2. Нормализованный контракт `DiscoveryRecord` (тип объекта, идентификаторы, атрибуты, источник, время) — единая точка входа для любого импорта.
3. Сервис реконсиляции: сопоставление по ключам (серийный номер → MAC → hostname → IP), формирование `diff`, режимы «применить автоматически» / «предложить к подтверждению».
4. Шина доменных событий (`outbox`) — исходящая интеграция.
5. Реестр `integration_source` с расписанием и учётными данными (секреты — в отдельном шифрованном хранилище).

Сами адаптеры (SNMP, Zabbix, AD/LDAP, Veeam, Git) в Phase 1–7 не разрабатываются.
