# Телефон: iPhone и Apple Watch

Мост живёт в `phone/` — это отдельный сервис со своим процессом, своей базой
и своим окружением. Ядро знает про него одну строку: адрес MCP-сервера.

```
iPhone / Apple Watch ──HTTP──▶ /v1/*  ──▶  phone.db  ──▶  /mcp ──MCP──▶ ядро
   ярлыки, Health Auto Export                                          Cursor
                       ◀──────  очередь заданий                        шлюз MCP
```

## Почему отдельный сервис, а не модуль ядра

Данные телефона приходят чаще всего остального вместе взятого и в самый
неудобный момент: пачкой за сутки, когда телефон дорвался до вайфая. Внутри
ядра это означало бы, что разбор чужого формата роняет диалог с владельцем.

Разъём наружу — MCP. Это не «ещё один REST», а протокол, который понимают
модели: ядро видит инструменты («что со мной сегодня»), а не таблицы. Тот же
сервер без единой правки подключается к Cursor и к общему шлюзу MCP, когда
сервисов станет больше одного.

Обратная сторона честная: мост — отдельный процесс, его нужно поднимать,
обновлять и следить за ним. Поэтому он умышленно маленький и без зависимостей
сверх FastAPI: протокол MCP реализован в `phone/mcp.py` своими силами.

## Внутрь — обычный HTTP

Ярлыки iOS не умеют MCP и не научатся: они умеют «получить содержимое URL».
Поэтому приём — простые POST с токеном устройства в заголовке
`X-Device-Token`.

| Запрос | Зачем |
| --- | --- |
| `POST /v1/devices/register` | поставить устройство на учёт, получить токен |
| `POST /v1/sync` | главный вход: всё накопившееся одним пакетом |
| `POST /v1/calls`, `/v1/messages`, `/v1/samples`, `/v1/workouts`, `/v1/state` | для простых ярлыков в один шаг |
| `GET /v1/outbox`, `POST /v1/outbox/ack` | телефон забирает задания и отчитывается |
| `GET /v1/summary` | та же сводка, что видит модель, — глазами |
| `GET /health` | жив ли мост и когда была синхронизация |

Пакет `/v1/sync` выглядит так:

```json
{
  "calls": [{"direction": "incoming", "status": "missed", "peer_name": "Саша",
             "peer_number": "+7 999 123-45-67", "started_at": "2026-09-21 08:30:00 +0300"}],
  "messages": [{"app": "imessage", "direction": "incoming", "peer_name": "Аня",
                "chars": 42, "ts": 1758443400}],
  "health": [{"metric": "sleep", "value": 6.7, "unit": "ч",
              "start": "2026-09-20T23:40:00+03:00", "end": "2026-09-21T06:22:00+03:00"}],
  "workouts": [{"kind": "Бег", "start": "…", "end": "…", "energy": 410}],
  "state": {"battery": 0.64, "charging": false, "focus": "Работа"}
}
```

Разбор намеренно терпимый. Время принимается эпохой, ISO 8601 и в виде
`2026-09-21 08:30:00 +0300`; числа — строками; метрики — под именами Apple
(`HKQuantityTypeIdentifierStepCount`), Health Auto Export (`step_count`) и
по-русски. Одна кривая строка не роняет пакет: она попадает в `rejected`,
остальное сохраняется. Иначе ярлык повторял бы сломанный пакет вечно.

Повторы обязательны к обработке: ярлык не помнит, что уже отправлял, и при
плохой связи пришлёт то же самое ещё раз. Каждое событие получает
`external_id` — свой, если телефон его дал, или отпечаток от «кто, когда,
сколько», если не дал. Повтор виден в ответе как `duplicates`.

Health Auto Export можно направить прямо на `/v1/sync`: формат
`{"data": {"metrics": […], "workouts": […]}}` мост понимает как свой.

Незнакомый раздел мост называет вслух: в ответе появляется `ignored`. Ярлык
собирается руками, и опечатка в названии раздела иначе выглядела бы удачей —
«принято 0» и ни слова о причине.

## Наружу — MCP

`POST /mcp` — Streamable HTTP. Реализованы обе эпохи протокола:

* **2026-07-28** — без сессий. Версия едет в `_meta`, метод и имя — в
  заголовках `Mcp-Method` и `Mcp-Name`. Именно это позволяет поставить
  впереди шлюз: он маршрутизирует и ограничивает по заголовкам, не разбирая
  тело. Заголовки обязаны совпадать с телом, иначе `-32020 HeaderMismatch`:
  иначе шлюз пропускал бы один запрос, а сервер выполнял другой.
* **2025-11-25 / 2025-06-18** — рукопожатие `initialize`. Так пока говорит
  большинство готовых клиентов.

Незнакомая версия получает `-32022` со списком поддерживаемых, `GET` и
`DELETE` на `/mcp` — `405`: потока событий и сессий в новой версии нет.

### Инструменты

| Инструмент | Что отвечает |
| --- | --- |
| `phone_today` | сводка дня: здоровье против нормы, звонки, переписка, тренировки |
| `phone_attention` | что требует внимания прямо сейчас |
| `phone_health` | одна метрика по дням: значения, среднее, норма, тренд |
| `phone_sleep` | сон за последние ночи вместе с пульсом покоя и HRV |
| `phone_calls` | журнал звонков, можно только пропущенные |
| `phone_messages` | кто и сколько писал (без текста) |
| `phone_workouts` | тренировки с часов |
| `phone_devices` | состояние моста: синхронизация, заряд, фокус |
| `phone_push` | положить задание телефону: уведомление, напоминание, ярлык |

Ресурсы: `phone://today`, `phone://attention`, `phone://devices`,
`phone://metrics`.

Каждый инструмент отдаёт две вещи сразу: текст для модели и структуру для
интерфейса. Текст уже осмысленный — «спал на два часа меньше обычного», а не
таблица замеров, которую модель пересчитает с ошибкой.

### Норма вместо нормативов

«8 231 шаг» ничего не значит без «обычно у тебя 11 тысяч». Поэтому всё
сравнивается с собственной нормой человека: медиана по последним
`PHONE_BASELINE_DAYS` дням, сегодняшний день в расчёт не идёт (иначе рекорд
сам себя объявил бы нормой), медиана — чтобы один марафон не задрал планку.

Вслух проговариваются только заметные отклонения: сон на пятую часть меньше,
пульс покоя выше на 8% (первый признак, что человек заболевает), HRV ниже на
четверть, шаги вдвое меньше, экранное время в полтора раза больше.

Ночь принадлежит утру: сон с 23:00 до 07:00 — это сегодняшняя ночь, а не
вчерашний вечер.

### Кто ждёт ответа

Пропущенный звонок и непрочитанное сообщение — одно и то же незакрытое дело,
поэтому они считаются вместе по человеку: последнее слово за собеседником —
значит, он ждёт. Перезвонили или ответили — дело закрыто. Свежее входящее не
считается долгом первые `PHONE_REPLY_GRACE_MINUTES` минут: человек мог просто
ещё не дойти до телефона.

## Приватность

Текст переписки не хранится. От сообщения остаются форма и метаданные: кто,
когда, сколько символов, было ли вложение. Для вопроса «кто ждёт ответа»
содержание не нужно, а утечка содержания — самое дорогое, что может случиться
с личным сервером. Включается осознанно: `PHONE_STORE_TEXT=1`.

Сервис слушает `127.0.0.1`. Наружу его выставляет nginx, и только `/v1`:
`/mcp` остаётся локальным, пока нет шлюза с собственной авторизацией. Токен
устройства показывается один раз при постановке на учёт, в базе лежит только
его хеш. `Origin` с чужой страницы получает `403` — защита от DNS rebinding.

Данные старше `PHONE_RETENTION_DAYS` (по умолчанию 400 дней) удаляются
фоновой уборкой.

## Что телефон реально может отдать

iOS закрыт, и честный список короче, чем хочется:

| Данные | Как | Ограничение |
| --- | --- | --- |
| Здоровье, сон, тренировки | ярлык «Найти образцы состояния здоровья» или Health Auto Export | автоматизация по времени, раз в час-сутки |
| Пропущенные звонки | автоматизация ярлыков не срабатывает на звонки | вручную кнопкой или из «Фокусирования»; часть звонков придётся вносить самому |
| iMessage и SMS | автоматизация «Когда я получаю сообщение» | только сам факт и отправитель; текст доступен ярлыку, но мост его не хранит |
| Экранное время | ярлыком не читается напрямую | вносится вручную или из сторонних выгрузок |
| Заряд, фокус, место | ярлык «Получить текущее состояние» | требует своей автоматизации |

Поэтому мост построен на «прислали — сохранили», а не на «мы опрашиваем
телефон»: опрашивать нечего, инициатива всегда на стороне iPhone.

## Настройка на телефоне

**1. Поставить устройство на учёт** (с самого сервера):

```bash
curl -s -X POST http://127.0.0.1:8820/v1/devices/register \
  -H 'Authorization: Bearer $PHONE_ENROLL_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"name": "iPhone", "kind": "iphone"}'
```

В ответе — токен. Он показывается один раз; положить его в «Заметки» ярлыка
или в связку ключей.

**2. Ярлык «Отправить здоровье»** (Команды → новый ярлык):

1. `Найти образцы состояния здоровья` — тип «Шаги», диапазон «сегодня»,
   группировать по дню.
2. Повторить для сна, пульса покоя, вариабельности, активных калорий.
3. `Текст` — собрать JSON вида `{"health": [...]}`.
4. `Получить содержимое URL`:
   * адрес `https://<ваш-домен>/phone/v1/sync`,
   * метод `POST`, заголовки `X-Device-Token: <токен>` и
     `Content-Type: application/json`,
   * тело — текст из шага 3.
5. Автоматизация: «Время суток», каждый час, «Запускать сразу» без
   подтверждения.

**3. Ярлык «Пропущенный звонок»** — кнопка на экране «Домой»: спрашивает имя,
отправляет `{"calls": [{"direction": "incoming", "status": "missed",
"peer_name": "…", "started_at": "<сейчас>"}]}` на `/v1/calls`.

**4. Автоматизация «Когда я получаю сообщение»** — отправляет
`{"messages": [{"app": "imessage", "direction": "incoming", "peer_name": "…",
"chars": …, "ts": …}]}` на `/v1/messages`. Текст в тело класть не нужно: мост
его всё равно не сохранит.

**5. Задания в обратную сторону.** Ответ `/v1/sync` содержит `outbox` —
очередь того, что ассистент хочет от телефона: показать уведомление,
завести напоминание, запустить ярлык. В ярлыке после отправки: пройти по
`outbox`, для `kind = notify` показать уведомление, затем отправить
`POST /v1/outbox/ack` со списком идентификаторов. Мгновенной доставки нет —
телефон забирает задания сам, когда выходит на связь.

**Apple Watch**: отдельного ярлыка не нужно. Часы пишут в «Здоровье» на
iPhone, и оттуда данные уезжают тем же ярлыком. Для тренировок полезна
автоматизация «Когда завершается тренировка» → отправить `/v1/workouts`.

## Подключение к ядру

В `/etc/assistant.env`:

```
MCP_SERVERS=phone=http://127.0.0.1:8820/mcp
MCP_PHONE_TOKEN=<PHONE_MCP_TOKEN моста>
```

Что появляется у ядра:

* `mcp.phone` в `/api/integrations` — видно, жив ли мост и сколько у него
  инструментов;
* блок «Телефон и здоровье» в промпте, когда в вопросе слышно про сон, шаги,
  самочувствие или пропущенные звонки;
* строка «Самочувствие» в утреннем брифинге и в голосовом;
* `phone` в `/api/overview` для веб-интерфейса;
* `GET /api/mcp` — что подключено, `POST /api/mcp/read` — прочитать,
  `POST /api/mcp/call` — вызвать то, что меняет мир, через движок действий:
  разрешения, подтверждение и журнал.

Чтение идёт напрямую: спросить, сколько человек спал, — не поступок. Всё
остальное (`phone_push`) — действие `mcp.tool.call` с уровнем риска MEDIUM,
то есть с подтверждением, и подтверждение спрашивается по-настоящему: ни один
путь не подставляет `user_confirmed` за владельца.

Границу между «спросить» и «сделать» ядро берёт не из названия инструмента, а
из разметки, которую даёт сам сервер: `annotations.readOnlyHint`. Инструмент
без такой пометки считается пишущим и через `/api/mcp/read` не проходит —
иначе сервер, забывший разметку, получал бы право менять мир по пути чтения.
Поэтому любой новый сервер MCP обязан помечать свои читающие инструменты; мост
телефона и финансовое приложение это делают.

## Подключение к Cursor и другим клиентам

Тот же сервер по stdio, без HTTP:

```json
{"mcpServers": {"jarvis-phone": {
  "command": "/opt/assistant/.venv/bin/python",
  "args": ["-m", "phone", "--stdio"],
  "env": {"PHONE_DB": "/opt/assistant/phone.db"}}}}
```

Через шлюз — как обычный сервер: шлюз ходит на `/mcp` с токеном, а ядру в
`MCP_SERVERS` указывается уже адрес шлюза. Инструменты ядро ищет по имени, а
не по серверу, поэтому приставка вроде `phone.phone_today` ничего не ломает.

## Деплой

```ini
# /etc/systemd/system/assistant-phone.service
[Unit]
Description=JARVIS phone bridge
After=network-online.target

[Service]
Type=simple
User=cursor
WorkingDirectory=/opt/assistant
EnvironmentFile=/etc/assistant-phone.env
ExecStart=/opt/assistant/.venv/bin/python -m phone
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Токен спрашивается у всех и всегда. Поблажки «с самой машины можно без
токена» здесь быть не может: мост слушает только loopback, а наружу его
выставляет прокси — значит запрос с улицы приходит к мосту с адресом
`127.0.0.1` и получал бы поблажку даром, вместе со здоровьем и геопозицией.
По той же причине пустой токен в настройках закрывает вход, а не открывает:
забытая строка в `/etc/assistant-phone.env` не должна означать открытый мост.

nginx выставляет наружу только приём:

```nginx
location /phone/v1/ {
    proxy_pass http://127.0.0.1:8820/v1/;
    client_max_body_size 8m;          # выгрузка здоровья за сутки бывает крупной
}
```

Проверка после установки:

```bash
curl -s http://127.0.0.1:8820/health
python -m pytest phone/tests -q
```

`/health` отвечает `degraded`, если ни одно устройство не синхронизировалось
дольше `PHONE_SILENCE_HOURS`: молчащий мост выглядит как «всё хорошо, данных
просто нет», и это худший вид поломки.
